# Project Notes for Coding Agents

- Project is active: do not preserve old internal APIs by default. For UI/admin API changes, use the simplest current contract unless compatibility is requested. Document every new feature.
- UI changes: run `npm run regen:ui-baselines` before committing; update README images (`doc/ui_*.png`) and hashes in `docs/refactoring/ui-visual-baseline.md`. Inspect regenerated images in full before cropping. UI text changes also require `npx prettier --check .` and checking English baselines (`doc/ui_proxy_en.png`, `doc/ui_logs_en.png`) for stray Chinese. The usage-statistics API contract is unit-sensitive: `overview` totals and byTarget/byModel `cost` are yuan strings, while trend `points[].cost` is a nano-CNY integer the UI divides by 1e9; derived values like averages must be computed with exact integer division on the nano values and only then converted to a decimal string (a naive float average of yuan values can come out as 0.014249999999999998 and format as 0.0142, one last-digit off versus the exact integer mean 0.0143); new baseline rows in the doc need a real SHA-256 hash (the regen script's row regex only matches a full 64-char `[0-9a-f]{64}` cell, so it rejects `PENDING` placeholders or truncated hashes like `f81eaa20a8d1…` — a row with a shortened hash makes the full-regen doc-sync step fail, so keep/restore the complete hash; for a panel-only change regenerating just the two task-detail baselines is enough, the other six stay byte-identical). To add a _new_ baseline without disturbing the existing ones, capture only it (`REGEN_BASELINES=1 npx vitest run test-node/ui/admin-ui.test.ts -t "<new test>"` — `screenshotDifference` writes the file and returns 0) and hand-fill its doc row; a full `npm run regen:ui-baselines` re-captures every page and can drift the stats page.
- `src/admin/static/app.css` is a cumulative stack of layout passes; later blocks in the file are not authoritative (e.g. the token card's 2x2 details grid is governed by a higher-specificity unmedia-queried `.stats-overview .stat-card-tokens .token-details` rule). When a layout change appears to have no effect, audit specificity via computed styles, not file order. Reusing a generic class in a new context (e.g. `.stat-card` in the task-detail summary) silently inherits later same-class rules (the stats block sets `clamp()` font-size + `white-space: nowrap`/ellipsis on `strong`), so the new context must explicitly override those properties — `overflow-wrap: anywhere` alone does not beat `white-space: nowrap`.
- The Electron Chromium (v40) does not support the `:sticky` pseudo-class — neither in stylesheets nor in `querySelector` — so "style only while a sticky element is pinned" cannot be done in CSS; gate such effects in JS or make the style safe in both states.
- The group summary row (`.log-group-fact-line`) clips right-to-left when too wide: children use `flex: 0 0 auto` and only the row keeps `overflow: hidden`. The model name is the one deliberate exception (`.log-group-fact-line > .log-model` gets `flex: 0 1 auto` + `min-width: 0` + ellipsis + `title`), so an over-long model truncates first and the metric chips (count/speed/cost) stay readable. Do not make another item (e.g. `.log-group-cost`) shrinkable — one accidental extra shrinkable child steals width from the metrics and silently truncates the wrong value. Chip sizing is width-budgeted for the default 330 px sidebar (10 px text, `padding: 0 5px`, `gap: 4px`): a realistic row (long model, 3-digit count and speed, 4-digit cost) fits exactly, so re-measure before enlarging the chips.
- The usage-trend y-axis is derived from a nice tick step (`tickStep = niceCeil(peak / trendTickIntervals)`, ladder includes 2.5) and stops at the first multiple of that step above the tallest stacked bar; a bare `niceCeil` of the peak jumped a ¥25 daily cost onto a ¥50 axis and left the whole upper half of the chart blank. Cost ticks are currency-formatted and the axis floor is one nano rather than one unit — that floor pinned every cheap task onto a ¥1 axis. The statistics baselines are captured in Token mode only, and the 2.5 rung keeps the baseline fixture's quarter-fraction axis byte-identical, so a cost-only axis change needs no baseline regen; still run the baseline tests to prove the token axis did not move.
- Verifying a `src/admin/static` change against the user's already-running portable instance is faster than rebuilding: read its admin port from `D:\Portable Program\llm_proxy\llm-proxy.json`, then have Playwright intercept `**/static/app.js` and serve the _instance's own_ script with the same patch applied to it. Serving the working tree's `app.js` on an older page dies at load (the page injects globals the newer script reads, e.g. `__SUGGESTED_STRIP_REQUEST_FIELDS__`) so nothing renders and the probe just times out. On real data, measure the tallest `.trend-bar` height against the 200 px plot instead of eyeballing screenshots — pixel diffing cannot tell a tight axis from a padded one.
- Checking admin-UI layout without patching the UI test file: a throwaway Node script that imports `createAdminServer` + `loadAdminStaticAssets` from `dist-node` with a stub `logService`, opens the page with the Playwright-bundled Chromium and screenshots `.log-list` at several `--sidebar-w` values is much faster. `loadAdminStaticAssets` serves the built `dist-node/**/static` copies, so run `npm run build` after editing `src/admin/static` (otherwise the harness silently renders stale CSS); when only the static files changed and `dist-node` is already compiled, `node dist-node/scripts/copy_static_assets.js` alone is enough. Compare `line.scrollWidth` with the container width to detect clipping numerically.
- The history list renders incrementally: `renderLogs` only rebuilds the task sections whose `logGroupRenderSignature` changed (cached in `state.logSections`) and leaves every other section's DOM nodes in place, so any state that changes the markup must be part of that signature - language, the group checkbox, expanded/loading flags, the selected row, and every per-record field a row prints. The task-detail panel skips rebuilds the same way through `state.taskPricingRendered`; a new panel block must show up in `taskPricingRenderSignature` (pricing payload, all three series, `state.activeTaskGroup`) or a refresh keeps the old DOM and the block looks like it never rendered. Diagnose admin-UI jank with a throwaway Playwright probe that wraps `window.renderLogs` / `window.renderTaskPricingPanel` with `performance.now()` and counts `MutationObserver` churn, backed by the read-only real `LogQueryService` on the production `traffic.db` - pixel diffing answers the wrong question here. The panel draws one `<circle>` per request, so its rebuild cost scales with the task's request count: it is the dominant per-tick cost once a panel is open. The JSON panes cache their last markup in `state.jsonPaneHtml` for the same reason: building the tree string is cheap (~80 ms for a several-hundred-kilobyte body) while assigning it is what costs seconds, because the tree is tens of thousands of `<details>` nodes - a selected record that is still pending used to be re-parsed on every auto-refresh tick, which froze the page. Time the panes by wrapping `window.renderJsonPane` with `performance.now()` (globals are reachable because `app.js` is a classic script, unlike the module-scoped `state`). Above `lazyJsonEntryLimit` the tree renders lazily: a node that starts collapsed is emitted with `data-json-lazy="1"` and an empty `.json-children`, and its children are only built when the pane's capture-phase `toggle` listener fires - so every path that opens a node programmatically (notably `restoreJsonPaneViewState` assigning `detail.open`, and the expand-one-level button) must materialize as well. Lazy fills go through the time-budgeted `jsonMaterializeQueue`: each node is filled _before_ it opens (never paints empty) and the drain is kicked from `setTimeout(0)`, never synchronously, so the expand click returns sub-millisecond instead of blocking ~300 ms on multi-megabyte bodies; non-lazy trees must still open nodes directly in the click handler because the queue skips unmarked nodes (the one-level-at-a-time UI test guards this). In this Chromium the `toggle` event is a queued task, so a frame can paint a programmatically opened lazy node before the capture-phase listener materializes it - the "empty next level" flash that motivated filling before opening. Proving a served-script patch actually executed: `getEventListeners` is DevTools-console-only and CDP `DOMDebugger.getEventListeners` returns an empty function description here, so instrument the served script with a global hit counter. A `clientWidth` read after the tree was mutated forces a synchronous re-layout of the whole pane - `materializeJsonNode` reads `jsonLineWidthCache` instead, kept fresh by a `ResizeObserver` and the render path; and the toggle listener's button refreshes must coalesce into one timeout per burst (`schedulePaneButtonsUpdate`) because per-toggle updates re-scan the whole tree hundreds of times. The residual lag on the _second_ expand click is layout, not JS: every fill re-lays-out the whole visible tree (16k+ nodes = 100-300 ms frame gaps per drain batch), so `.json-row` carries `content-visibility: auto` (app.css) to contain invalidation and skip offscreen subtrees - and rows the browser has never realized then need an accurate `contain-intrinsic-size`, which `countJsonLinesWalk` estimates from the subtree's _current open state_ (collapsed nodes/strings count as their single summary line) and `jsonRowHtml` bakes into the row's inline style; `materializeJsonNode` must refresh the parent row's hint after filling or the scrollbar stays underestimated ~6x (a hint of `auto 18px` alone gives a scrollHeight that never reaches the real bottom). Chromium still realizes a row that scrolled into view one frame _after_ it paints (a blank flash while scrolling), so the rows around the viewport are pre-realized by `updateJsonRowWindow` + the per-pane scroll-armed `requestAnimationFrame` watcher (rAF runs before that frame's paint; clamping the hint into the cached row list after a rebuild or the anchor row is `undefined`). Never use an always-on rAF loop there: a self-perpetuating rAF chain never settles under `page.clock` and hangs fake-clock tests (the metrics auto-refresh test timed out). Batch style writes after rect reads - interleaved write/read thrashing cost ~900 ms per scroll event, windowed + batched costs 5-20 ms. Measure smoothness with real `page.mouse.wheel` (the input pipeline, where the scroll task runs before the frame's rendering), not programmatic `scrollTop`; a probe that scans every visible row's `offsetHeight` manufactures the very frame gaps it claims to measure. Prove it with a `PerformanceObserver(['longtask'])` plus an rAF-gap probe (gaps > 100 ms = freeze) and `scrollHeight` against a no-CV baseline, not eyeballs; CDP `Performance.getMetrics` `LayoutCount` deltas separate layout churn from script cost. `jsonLineCache` is a WeakMap: primitives are not valid keys (`WeakMap.set` on a string throws `Invalid value used as weak map key`), and because `selectLog` swallows errors a thrown render leaves a silently empty pane - surface the failure by wrapping the suspect function in the served script. Prove responsiveness by timing inside the click handler (sub-ms target) and polling `data-json-lazy-done` for drain settle - interval-based timestamps mislead because timers get clamped while the main thread is busy. Prove a forced rebuild with the formatted-string toggle button, which re-renders the same pane with different markup, and compare row/open/scroll counts before and after rather than eyeballing. In-flight rows are swept through `GET /api/logs/records?ids=a,b` (body-free rows plus `pending`) because one detail read inflates every stored chunk of a record: 22 pending records cost ~100-200 ms of blocked event loop per tick as individual detail requests, and the same batch is ~2 ms. Batch rows carry no bodies, so the selected record must stay out of `refreshedIds` for the caller to still fetch its detail. In UI fixtures, an array that a stub method builds per call cannot be hoisted into a module-level const - values that read mutable test flags (`has_summary: useSummarizedLogFixture`) freeze at module load and the assertion silently sees the old flag. Key patching also woke up Chromium's scroll anchoring: an incremental render replaces one task section while every neighbour stays put, so the browser anchors on an unchanged node and scrolls the list down by the inserted body's full height - which hid the whole second level whenever the expanded task's header sat on the scrollport's content top (for the first section that is any `scrollTop` of ~1 px, so it looked like "only the top entry does this"). `.log-items` sets `overflow-anchor: none` because a full innerHTML replace used to destroy the anchor node; verify numerically with `#logItems.scrollTop` before/after the caret click plus the first `.log-item`'s rect against the scrollport, and keep the pinned-header UI test (large list + `useLargeGroupLogFixture`, which now serves the tall record page for any group id) as the guard. The same sticky geometry bites expansion a second way: a collapsed section is too short for the sticky constraint, so a header that is partly scrolled out of the scrollport is merely clipped, and the body it is about to grow lets it stick at the top and paint over the first record by exactly the clipped height. `toggleLogGroupBody` aligns the header with the scrollport's content top (`logListContentTop`, the same line `collapseLogGroup` tests for pinning) before it expands, which makes the sticky offset zero; measure it as the first `.log-item`'s rect top minus the header's bottom instead of eyeballing the overlap.
- Two refresh contracts on that page: the automatic tick re-reads every group already on screen, so its `limit` must stay inside the API's `maximum: 500` (`LOG_GROUP_PAGE_MAX_LIMIT`) and a truncated page must carry over the groups the user paged past (`mergeLogGroupSummaries` `keepMissing`, pagination continuing from `state.logGroups.length`) - before that, more than 500 loaded groups made every tick 400 with `FST_ERR_VALIDATION`. `loadLogs` coalesces a request that arrives while another is in flight (`state.logsQueued`) instead of dropping it, and the pending-row sweep reads one rotating slice per tick (`PENDING_REFRESH_BATCH` / `PENDING_REFRESH_CONCURRENCY` / `state.pendingSweepCursor`), so tests that count `detailReads` only ever see the rows in the current batch.
- The task header (`.log-group-head`) is a 3-row grid whose control column (`.log-group-controls`: checkbox plus the caret button — the ⓘ task-detail icon button was removed once the head itself became details-only, and the caret needs an explicit `grid-row: 3` because auto-placement would otherwise pull it up to the vacated second row) and `.log-group-summary` share those rows via `grid-template-rows: subgrid`, so each control can be vertically centered against its text row (time / model+cost / target) with `align-items: center`. Keep header controls in that shared-row structure when moving or aligning them — separate stacked grids with manual gaps cannot reliably align across columns. Interaction model: a head click (or Enter/Space) only opens the task-detail panel and never touches the body expansion. Expanding/collapsing the request list is the caret button's exclusive job (`.log-group-caret`, `data-group-toggle` — a real `<button>` that activates natively on Enter/Space, so the head's keydown handler must keep skipping `button` targets); expanding through it lazy-loads the group's records via `toggleLogGroupBody`, so test flows that need a group's second level click the caret, not the head. In Playwright locators, `[data-group-id]` is the head div itself (the `.log-group` section doesn't carry it), so `[data-group-id="…"] .log-group-head` silently matches nothing and the click hangs until the 30 s test timeout — scope with `.log-group:has([data-group-id="…"])` or use the element directly.
- Target-card reordering (the `⠿` handle in `.target-title`) uses pointer events, not the HTML5 drag API: pointerdown runs `collectPairs()` and then moves the card nodes in the DOM live, and the drop maps DOM order back to `state.pairs` through each card's `data-target-index` before re-rendering. Never `collectPairs()` after the nodes moved (the DOM order no longer matches those indices), and make the drop side follow the layout axis — grid rows compare the pointer against the x midpoint, a single-column stack against the y midpoint, otherwise narrow layouts insert on the wrong side.
- The `.target-head` name input is a default-sized `<input>` (fixed ~95 px client width; longer names clip — `scrollWidth` slightly exceeds `clientWidth` — instead of reflowing), so renaming a fixture target never moves Test/Metrics/Delete and only changes glyph pixels (pixel-diff ratio ~0.0007, identical image size). Such a rename therefore needs only the affected baselines re-captured with the selective `-t` regen plus those two doc hash rows; the other six stay byte-identical.
- Run Vitest and UI baseline commands from an uppercase drive path (`cd /D/...`); lowercase `d:` can duplicate the runtime. After `npm run rebuild:electron`, run `npm rebuild better-sqlite3` before Node tests; an ABI mismatch surfaces at test start as `was compiled against a different Node.js version` / `cannot open shared object`.
- The task-detail (pricing) baseline uses an adaptive viewport: after the panel opens, the test resizes to the panel's scrollHeight + 52 (like the statistics baseline), because the panel is inset:0 with its own scroll — a fixed-height viewport silently hides the bottom of the panel in the PNG. Adding a panel block therefore changes the baseline image height; update the doc row. If a newly added panel section is missing from a regenerated baseline, compare the element's bounding rect against the panel's `clientHeight` (and `scrollHeight`) before assuming the screenshot is wrong — the panel simply isn't scrolled in the capture.
- The task-detail summary header (`.task-summary`) is a stack: target line, then a 2-row x 4-column card grid — the model is the first grid card (the user explicitly rejected the full-width-line layout; `fitTaskSummaryValues` in app.js shrinks the model's `strong` 1 px at a time, floor 12 px, until it fits one line before wrapping, and re-runs on every panel re-render), and the time bar spans the remaining 3 cells. The Time range sub-card is a three-column (label | date | time) grid: the “Time range” label shares the start-time row on the left (the user rejected a top-header placement for it), and both the start- and end-date badges always render — even for same-day ranges — so the two date badges sit in one column and the two timestamps in the other; a thin ↓ arrow row (time column only, no badge) separates the lines and is rendered only when both exist — the user asked for the two time centers ~30 px apart (time rows use line-height 1, the arrow row line-height 0.8; if you need to retune, measure with a getBoundingClientRect center-gap probe, don't eyeball). Both date badges carry distinct classes (`task-time-date-start`/`-end`) with explicit grid placement in app.css: the markup is written by `taskTimeRangeHtml` in app.js, and this exact pair of class names is what the CSS anchors on — a previous round's badges only had the shared `task-time-date` class while the CSS targeted `-start`/`-end`, so the badges silently fell back to grid auto-placement and the rows misaligned (verify with getBoundingClientRect probes, not eyeballs, before shipping alignment changes). Also: a bare `<small>` with no class never matches a `.small` rule, and grid auto-placement can make a broken layout look plausible — always confirm selectors match the rendered markup before claiming a spacing/alignment change took effect.
- The usage-statistics page is rendered on demand by `loadStatistics`/`loadStatisticsOptions` with inline `state.language === "en" ? … : …` strings (not `data-i18n`); any language switch must therefore re-run that render, which `setLanguage` does only when the page was already loaded. New language-dependent UI must be reachable from an existing re-render path.
- Regenerated UI-baseline PNGs can change bytes/hashes (encoder metadata non-determinism) while remaining pixel-identical; before treating a baseline change as a visual regression, diff committed vs regenerated images pixel-wise (e.g. `pixelmatch` + `pngjs`, threshold 0.1, expect 0 differing pixels). If the test baseline was committed from another machine, local regen can shift hashes for every page at once — compare against a stash of the pre-change source to separate your effect from environment drift. Environment drift can also shift the _document height_ by a few px (fractional-pixel rounding) with identical visible content; `screenshotDifference` therefore tolerates a height delta ≤ 4 px with near-white extra rows — do not reintroduce strict size assertions there. The inverse trap: a hash change with a pixel-identical image can also mean the on-disk PNG is a _stale_ regeneration from before the code change took effect (non-`REGEN_BASELINES` `screenshotDifference` only reads and never writes, so a green test proves nothing about the baseline file). When a baseline appears unresponsive to a UI change, verify in order: (1) the served static assets actually contain the new string — the vitest harness serves `src/admin/static` but the built app serves the `dist-node` copies, so check both; (2) the new DOM content actually renders — a throwaway `page.evaluate` dump of the changed text/nodes is the fastest conclusive check, faster than pixel archaeology; (3) then pixel-diff the on-disk file against HEAD.
- `npm run regen:ui-baselines` can drift `ui_stats_*` for a pre-existing reason unrelated to your change: the trend grouping select in `app.js` is read via `$("statsBreakdown")?.value || "model"` before the select may exist, so the stats page can be captured with the "model" breakdown instead of the default "total" (a different legend/bar colors and ~2px document height). If the stats page is the only visual change and you did not touch stats code, resolve the conflict by comparing hashes, not by restoring blindly: the committed `ui_stats_*` PNG bytes have at times not matched the committed doc hashes (the two artifacts were captured in different environments), while a local regen converges exactly to the doc hashes — in that case adopt the regenerated stats PNGs (no doc edit needed) and re-diff the PNGs pixel-wise to prove your change left the stats page visually untouched. Restore the committed PNGs only if the regen hash matches neither. Note that restoring the doc via `git checkout` also resets any uncommitted table fixes in it (e.g. a restored/added column) — re-apply those after the restore.
- Playwright `page.waitForResponse` waits for a response received _after_ the call; a response that already delivered can miss it and the wait hangs until the 30 s timeout (observed when a handler fires a burst of fetches and an earlier-registered sibling wait or prior assertions consume the window). Register all series waits in one `Promise.all` together with the click that triggers the requests; for re-open/re-render flows where the requests already fired, skip the response waits and let the retrying `expect` assertions wait on the rendered DOM instead. Likewise, when duplicating an SVG chart for a second metric give the new chart its own container class and share only the inner element classes — reusing the original container class makes strict-mode selectors like `#pricingPanel .token-chart svg` in the UI tests resolve to two elements. The same strict-mode trap applies to tags: the breakpoint test selects `header:not(.summary-dialog-head)` on the page, so any new `<dialog>` head must be a `<div>` (not a `<header>`) or it silently breaks that test the moment the dialog is added to the DOM.
- In the pinned playwright-core (1.62.0) `Request.postData()` / `Request.postDataJSON()` (reached via a page `Response.request()`) are _synchronous_ methods (`null | string` / `null | Serializable`) — do not `await` them; use `postDataJSON()` to assert POST bodies. `expect(locator).toHaveValues([...])` also misbehaves in this version: it throws a strict-mode violation even for a stable two-element locator, so assert per element with `nth(i)` + `toHaveValue()` instead. Note: the `APIResponse` returned by `page.request` (APIRequestContext) has `request()` in the typings but **not at runtime** in this version (`TypeError: request is not a function`), so body assertions must go through page `response` events / `waitForResponse`, not through the API request context. Timer-driven UI (auto-refresh intervals) is testable without wall-clock waits via `page.clock.install()` before `goto` + `page.clock.runFor(ms)` — in-page timers only advance when you run the clock forward, while `expect.poll`/web-first assertions still use real time; remember other app timers (e.g. log auto-refresh) fast-forward too and may fire extra stubbed fetches. A refresh timer that guards against overlapping requests (the metrics auto-refresh returns early while `metricsState.loading` is true) silently drops a tick when the previous fetch is still in flight, so clock-driven tests must first wait for that settle signal (the metrics dialog's `#metricsRefresh` button is disabled while loading — `toBeEnabled()` is the cheap wait) before `runFor`, or the call count comes up short on slow CI runners. Lint forbids both `!` and null-stripping `as` casts, so keep the target type nullable and guard (`const body = req.postDataJSON() as {…} | null; if (body === null) throw …;`).
- `npm run build` type-checks `test-node/**` and `scripts/**`; verify unrelated errors against clean source, apply the smallest type-only fix, and disclose it.
- Admin service methods are optional and routes register only when present. For a 404, compare `src/app/runtime.ts` wiring with `LogAdminService`, `PairAdminService`, `SummaryModelAdminService`, and `ModelCatalogAdminService`; add new-route coverage to the assembled-app smoke test in `test-node/app/runtime.test.ts`. Fastify schema-validation 400s carry the error code `FST_ERR_VALIDATION` (the error handler only falls back to `bad_request` when the error has no `code`), so tests asserting the code must expect `FST_ERR_VALIDATION`.
- UI modifications require screenshot verification. Clean temporary files and processes when done.
- After every task, build the portable executable: `npm run build && npm run rebuild:electron && npx electron-builder -w portable --publish never`.
- Native module ABI: run `npm rebuild better-sqlite3` only before the final `npm run rebuild:electron`; never run the Node rebuild after Electron rebuild or before packaging, or the portable app will contain a Node ABI binary and fail at startup.
- Config save no longer restarts a listener whose listen address and enabled flag are unchanged: `ProxyManager` routes such updated pairs to `ProxyRuntimeRegistry.reloadPair()`, which swaps `{ pipeline, activeRequests }` as one object on the live listener and drains the superseded generation (ADR-011). Replacing only the pipeline leaves `resources.activeRequests` on the superseded registry, so `diagnostics()` double-counts the old requests and never sees the new ones - always swap both together. Traffic log services are cached per runtime entry by `resolved log_root + redact_logs`; reusing an instance also avoids `markPendingPricingInterrupted()` rewriting in-flight `pending` pricing rows. Verify the real save path (unit/UI tests do not cover in-flight semantics) by spawning `dist-node/src/main.js` in a throwaway cwd with `--port --config-file --log-root --application-config --no-browser`, opening an SSE request through the proxy port and `PUT /api/pairs` mid-stream: before the fix it returned ~2 s later on a new port with a `terminated` stream, now it returns in milliseconds on the same port with every chunk delivered.
- Execution history logs: `D:\Portable Program\llm_proxy\logs`.
- Traffic-log forensics without touching native modules: open `logs/traffic.db` with Python's stdlib `sqlite3` — after `npm run rebuild:electron`, `better-sqlite3` carries the Electron ABI and a plain `node -e` require fails with `NODE_MODULE_VERSION`. Streamed bodies are stored in `body_chunks` (`record_body_chunks.chunk_hash` → `body_chunks.data`); `codec=deflate-raw-1` needs `zlib.decompress(data, -15)`, not the zlib wrapper. Judge token/speed claims against the upstream engine's `/metrics` counters (`prompt_tokens_by_source_total{source="local_compute"}` ÷ `request_prefill_time_seconds_sum` gives real prefill throughput) instead of trusting history chips: the Prefill chip divides by `first_token_ms`, which also covers proxy body parsing and upstream tokenization, so it is only an approximation. Triage an all-`unpriced` task the same way: pull the response `usage` object out of `body_chunks` and read it against `pricing_reason` — a whole task stuck on `invalid_usage` on an OpenAI-compatible upstream is normally an explicitly `null` optional field (vLLM sends `prompt_tokens_details: null` when cache accounting is off), not malformed token counts. Conversely, a task that shows only end-to-end speed is expected, not a bug: `first_token_ms` and `decode_window_ms` are sampled only for SSE responses, so buffered non-stream requests have neither and the UI must fall back to end-to-end.
- The portable exe is an NSIS wrapper around a 7z-compressed `win-unpacked` payload: raw string search in the `.exe` misses code; verify build contents in `release/win-unpacked/resources/app.asar` (or extract the 7z payload with 7-Zip). When an LLM Proxy instance is already running, do not assume it is your own test launch — the exe name and version are unchanged across consecutive same-version builds; check the process creation time and extraction path (portables unpack to a `Temp` dir) before querying or killing it, and only kill processes you started.
- Release: `npm version <patch|minor|major> --message "chore(release): %s"`, then push branch and tag (`git push origin main vX.Y.Z`). Publishing occurs only from `v*` tags; tag pushes rerun CI.
- CI without `gh`: query the public Actions REST API with `curl` (`/actions/runs`, details, `/jobs`). Job logs require a token (one is retrievable via `git credential fill`); diagnose `npm run check` by running `format:check`, `lint`, `typecheck`, `test`, and `build` separately. UI tests launch the Playwright-bundled Chromium (CI downloads it with `npx playwright install chromium`); never fall back to the OS Chrome, whose auto-updates on GH runners can hang `chromium.launch` (override with `CHROME_PATH` if needed). Poll that endpoint until every run for the pushed sha reports a terminal `status`, then exit the loop immediately - never sleep a fixed number of iterations, which keeps the session blocked for minutes after the workflows are already green.
