# Project Notes for Coding Agents

- This project is still in active development. Do not preserve old internal API behavior by default.
- When changing UI/admin API contracts, prefer the simplest current design over backward-compatible shims unless the user explicitly asks for compatibility.
- Whenever implementing a new feature, add or update the corresponding documentation.
- When the UI is changed, the README screenshots (`doc/ui_*.png`, referenced by README.md and README.cn.md) must be updated before committing: run `npm run regen:ui-baselines` to re-capture them and refresh the baseline hashes in `docs/refactoring/ui-visual-baseline.md`.
- When visually verifying regenerated baseline screenshots, view the FULL image first instead of cropping sub-regions based on where you assume the content is. The layout shifts after UI changes (e.g. an expanded log group sits at the top of the list, not the bottom), so a wrong crop looks like a blank area and can mislead you into suspecting the code change didn't take effect. Only crop to zoom in after locating the relevant area in the full image.
- On this machine, vitest must be launched from the uppercase drive letter (`cd /D/...`); from lowercase `d:` the runtime fails with "Vitest failed to find the current suite" (duplicate vitest runtime via path-case mismatch). `npm run regen:ui-baselines` is affected the same way.
- `npm run rebuild:electron` (part of the portable-exe build flow) recompiles native modules (better-sqlite3) against Electron's ABI, after which Node-based test runs fail with a NODE_MODULE_VERSION mismatch. Run `npm rebuild better-sqlite3` to restore the Node ABI before running vitest again.
- The root `tsconfig.json` that `npm run build` runs also type-checks `test-node/**` and `scripts/**`, so a type error in any test or script file (e.g. an index access that is `undefined` under `noUncheckedIndexedAccess`) blocks the production build and therefore the mandatory portable-exe step. When the build fails in a file your task did not touch, it is a genuine pre-existing blocker: verify it against the clean source (e.g. `git stash` + re-run tsc), unblock it with a minimal type-only fix, and disclose it — rather than assuming the failure is caused by your own changes.
- After UI text (i18n) changes, run the full `prettier --check .` before committing: recent commits have repeatedly broken CI's `format:check` by committing HTML/JS edits in a non-prettier format (e.g. collapsed `><tag ...>` blocks). Fix by hand-applying prettier's hunks to the touched areas only.
- When a task changes any UI text (new i18n keys, renamed labels), regenerate the baselines (`npm run regen:ui-baselines`) within the same task and inspect the FULL English baselines (doc/ui_proxy_en.png, doc/ui_logs_en.png) for leftover hardcoded Chinese before committing. In one incident the baselines were captured before an i18n fix and committed as-is, so the English History screenshot shipped with a Chinese "总结模型配置" toolbar button and the user had to catch it. The current baseline set is only these 4 proxy/history screenshots, not per-page shots.
- The recent execution history logs are located in the D:\Portable Program\llm_proxy\logs directory. Check them when needed.
- Seam blind spot in admin API wiring: the admin service interfaces (`LogAdminService`, `PairAdminService`, `SummaryModelAdminService`) declare many methods as optional, and `src/admin/admin-server.ts` only registers a route when the method is present (`X?.bind` / `if (X)` checks), while `src/app/runtime.ts` hand-assembles those service objects as object literals — so a dropped binding compiles silently, passes every test (unit tests hand-craft the service objects, UI tests mock `fetch`), and 404s only at runtime. When a route 404s at runtime, first diff the object assembled in `src/app/runtime.ts` against the interface's optional methods. When adding a new admin route or optional service method, extend the E2E route smoke test in `test-node/app/runtime.test.ts` that boots the real assembled app (it currently covers all `/api/logs` routes).
- UI-related modifications must be tested in practice by taking screenshots to verify that the interface meets expectations and is aesthetically pleasing and reasonable.
- After development is complete, the temporarily created files and processes must be cleaned up.
- After each task is completed, generate a new portable exe by executing the command: `npm run build && npm run rebuild:electron && npx electron-builder -w portable --publish never`.
- To create and publish a new version: run `npm version <patch|minor|major> --message "chore(release): %s"` — it bumps the version in **both** `package.json` and `package-lock.json` (this repo has no CHANGELOG), commits, and creates a `vX.Y.Z` tag — then push **both** the branch and the tag (`git push origin main vX.Y.Z`). `release.yml` builds the Electron/CLI artifacts from the version in `package.json` on both branch and tag pushes, but its publish job only runs on a `v*` tag ref, so **the GitHub Release is created/uploaded only when the tag is pushed** — pushing the version-bump commit alone builds but does not publish. Pushing the tag also re-triggers `ci.yml` (it fires on any push), so expect one extra (harmless) CI/Release run per release.
- CI status can be checked without the `gh` CLI (not installed here) and without a token, because the repo is public: `curl` the GitHub Actions REST API — `GET /repos/{owner}/{repo}/actions/runs?per_page=N` (list runs, match by `head_sha`), then `GET /actions/runs/{id}` and `GET /actions/runs/{id}/jobs` for per-job and per-step status/conclusion. **Job logs (`GET /actions/jobs/{id}/logs`) return 403 without a token even on a public repo**, so you can see _which step_ failed but not its text. The Node job's single `npm run check` step runs `format:check` → `lint` → `typecheck` → `test` → `build`, so the failing step name does not say which subcommand broke — diagnose by running each of those stages locally in turn.
- Retrospective rule for this document: write a brief retrospective after a task ONLY when it surfaced a pitfall or lesson worth recording; skip it if the task went smoothly. Every candidate bullet must pass all of the following checks BEFORE being added, and the candidate fails if any check fails:
  1. Redaction test: rewrite the candidate with all task/incident specifics removed (which button, which page, which run, which numbers). If the remaining sentence no longer independently prevents a future mistake, discard the candidate — it is task-specific.
  2. Fact verification: every factual claim about the codebase in the bullet (counts, "most/some/all X are Y", method names, file paths) must be verified against the actual source (grep/rg) before writing; do not record unverified generalizations (prefer "many" over "most" unless you counted).
  3. What to record: only (a) project-wide, non-obvious characteristics (verified to hold in more than one place), (b) reusable debugging heuristics, and (c) forward-looking "when you do X, do Y" rules. Prefer descriptive references ("the E2E route smoke test in test-node/app/runtime.test.ts that boots the assembled app") over exact volatile names (test titles, line numbers, specific error strings) that go stale.
  4. Dedup: re-read this document before writing; if a similar lesson already exists, merge/rewrite that existing bullet in place instead of adding a second, overlapping one.
  5. Self-audit: after editing, run `git diff AGENTS.md` and confirm the diff contains ONLY the intended bullet(s) added or rewritten — no other line altered (wording, bullet order, or whitespace, including Chinese text); then run `npx prettier --check AGENTS.md` and confirm it passes.
