# Project Notes for Coding Agents

- Project is active: do not preserve old internal APIs by default. For UI/admin API changes, use the simplest current contract unless compatibility is requested. Document every new feature.
- UI changes: run `npm run regen:ui-baselines` before committing; update README images (`doc/ui_*.png`) and hashes in `docs/refactoring/ui-visual-baseline.md`. Inspect regenerated images in full before cropping. UI text changes also require `npx prettier --check .` and checking English baselines (`doc/ui_proxy_en.png`, `doc/ui_logs_en.png`) for stray Chinese. The usage-statistics API contract is unit-sensitive: `overview` totals and byTarget/byModel `cost` are yuan strings, while trend `points[].cost` is a nano-CNY integer the UI divides by 1e9; new baseline rows in the doc need a real SHA-256 hash (the regen script's row regex only matches a full 64-char `[0-9a-f]{64}` cell, so it rejects `PENDING` placeholders or truncated hashes like `f81eaa20a8d1…` — a row with a shortened hash makes the full-regen doc-sync step fail, so keep/restore the complete hash; for a panel-only change regenerating just the two task-detail baselines is enough, the other six stay byte-identical). To add a _new_ baseline without disturbing the existing ones, capture only it (`REGEN_BASELINES=1 npx vitest run test-node/ui/admin-ui.test.ts -t "<new test>"` — `screenshotDifference` writes the file and returns 0) and hand-fill its doc row; a full `npm run regen:ui-baselines` re-captures every page and can drift the stats page.
- `src/admin/static/app.css` is a cumulative stack of layout passes; later blocks in the file are not authoritative (e.g. the token card's 2x2 details grid is governed by a higher-specificity unmedia-queried `.stats-overview .stat-card-tokens .token-details` rule). When a layout change appears to have no effect, audit specificity via computed styles, not file order. Reusing a generic class in a new context (e.g. `.stat-card` in the task-detail summary) silently inherits later same-class rules (the stats block sets `clamp()` font-size + `white-space: nowrap`/ellipsis on `strong`), so the new context must explicitly override those properties — `overflow-wrap: anywhere` alone does not beat `white-space: nowrap`.
- The Electron Chromium (v40) does not support the `:sticky` pseudo-class — neither in stylesheets nor in `querySelector` — so "style only while a sticky element is pinned" cannot be done in CSS; gate such effects in JS or make the style safe in both states.
- The group summary row (`.log-group-fact-line`) clips right-to-left when too wide: children use `flex: 0 0 auto` and only the row keeps `overflow: hidden`. The model name is the one deliberate exception (`.log-group-fact-line > .log-model` gets `flex: 0 1 auto` + `min-width: 0` + ellipsis + `title`), so an over-long model truncates first and the metric chips (count/speed/cost) stay readable. Do not make another item (e.g. `.log-group-cost`) shrinkable — one accidental extra shrinkable child steals width from the metrics and silently truncates the wrong value. Chip sizing is width-budgeted for the default 330 px sidebar (10 px text, `padding: 0 5px`, `gap: 4px`): a realistic row (long model, 3-digit count and speed, 4-digit cost) fits exactly, so re-measure before enlarging the chips.
- Checking admin-UI layout without patching the UI test file: a throwaway Node script that imports `createAdminServer` + `loadAdminStaticAssets` from `dist-node` with a stub `logService`, opens the page with the Playwright-bundled Chromium and screenshots `.log-list` at several `--sidebar-w` values is much faster. `loadAdminStaticAssets` serves the built `dist-node/**/static` copies, so run `npm run build` after editing `src/admin/static` (otherwise the harness silently renders stale CSS); compare `line.scrollWidth` with the container width to detect clipping numerically.
- The task header (`.log-group-head`) is a 3-row grid whose control column (`.log-group-controls`: checkbox, task-detail icon, caret) and `.log-group-summary` share those rows via `grid-template-rows: subgrid`, so each control can be vertically centered against its text row (time / model+cost / target) with `align-items: center`. Keep header controls in that shared-row structure when moving or aligning them — separate stacked grids with manual gaps cannot reliably align across columns.
- Target-card reordering (the `⠿` handle in `.target-title`) uses pointer events, not the HTML5 drag API: pointerdown runs `collectPairs()` and then moves the card nodes in the DOM live, and the drop maps DOM order back to `state.pairs` through each card's `data-target-index` before re-rendering. Never `collectPairs()` after the nodes moved (the DOM order no longer matches those indices), and make the drop side follow the layout axis — grid rows compare the pointer against the x midpoint, a single-column stack against the y midpoint, otherwise narrow layouts insert on the wrong side.
- Run Vitest and UI baseline commands from an uppercase drive path (`cd /D/...`); lowercase `d:` can duplicate the runtime. After `npm run rebuild:electron`, run `npm rebuild better-sqlite3` before Node tests; an ABI mismatch surfaces at test start as `was compiled against a different Node.js version` / `cannot open shared object`.
- The task-detail (pricing) baseline uses an adaptive viewport: after the panel opens, the test resizes to the panel's scrollHeight + 52 (like the statistics baseline), because the panel is inset:0 with its own scroll — a fixed-height viewport silently hides the bottom of the panel in the PNG. Adding a panel block therefore changes the baseline image height; update the doc row. If a newly added panel section is missing from a regenerated baseline, compare the element's bounding rect against the panel's `clientHeight` (and `scrollHeight`) before assuming the screenshot is wrong — the panel simply isn't scrolled in the capture.
- The task-detail summary header (`.task-summary`) is a stack: target line, then a 2-row x 4-column card grid — the model is the first grid card (the user explicitly rejected the full-width-line layout; `fitTaskSummaryValues` in app.js shrinks the model's `strong` 1 px at a time, floor 12 px, until it fits one line before wrapping, and re-runs on every panel re-render), and the time bar spans the remaining 3 cells. The Time range sub-card is a three-column (label | date | time) grid: the “Time range” label shares the start-time row on the left (the user rejected a top-header placement for it), and both the start- and end-date badges always render — even for same-day ranges — so the two date badges sit in one column and the two timestamps in the other; a thin ↓ arrow row (time column only, no badge) separates the lines and is rendered only when both exist — the user asked for the two time centers ~30 px apart (time rows use line-height 1, the arrow row line-height 0.8; if you need to retune, measure with a getBoundingClientRect center-gap probe, don't eyeball). Both date badges carry distinct classes (`task-time-date-start`/`-end`) with explicit grid placement in app.css: the markup is written by `taskTimeRangeHtml` in app.js, and this exact pair of class names is what the CSS anchors on — a previous round's badges only had the shared `task-time-date` class while the CSS targeted `-start`/`-end`, so the badges silently fell back to grid auto-placement and the rows misaligned (verify with getBoundingClientRect probes, not eyeballs, before shipping alignment changes). Also: a bare `<small>` with no class never matches a `.small` rule, and grid auto-placement can make a broken layout look plausible — always confirm selectors match the rendered markup before claiming a spacing/alignment change took effect.
- The usage-statistics page is rendered on demand by `loadStatistics`/`loadStatisticsOptions` with inline `state.language === "en" ? … : …` strings (not `data-i18n`); any language switch must therefore re-run that render, which `setLanguage` does only when the page was already loaded. New language-dependent UI must be reachable from an existing re-render path.
- Regenerated UI-baseline PNGs can change bytes/hashes (encoder metadata non-determinism) while remaining pixel-identical; before treating a baseline change as a visual regression, diff committed vs regenerated images pixel-wise (e.g. `pixelmatch` + `pngjs`, threshold 0.1, expect 0 differing pixels). If the test baseline was committed from another machine, local regen can shift hashes for every page at once — compare against a stash of the pre-change source to separate your effect from environment drift. Environment drift can also shift the _document height_ by a few px (fractional-pixel rounding) with identical visible content; `screenshotDifference` therefore tolerates a height delta ≤ 4 px with near-white extra rows — do not reintroduce strict size assertions there.
- `npm run regen:ui-baselines` can drift `ui_stats_*` for a pre-existing reason unrelated to your change: the trend grouping select in `app.js` is read via `$("statsBreakdown")?.value || "model"` before the select may exist, so the stats page can be captured with the "model" breakdown instead of the default "total" (a different legend/bar colors and ~2px document height). If the stats page is the only visual change and you did not touch stats code, restore the committed `ui_stats_*` baseline and doc hashes instead of adopting the drift (the drifted hash even differs between regen runs, so the pixel diff — not the hash — shows what your change did). Note that restoring the doc via `git checkout` also resets any uncommitted table fixes in it (e.g. a restored/added column) — re-apply those after the restore.
- Playwright `page.waitForResponse` waits for a response received _after_ the call; a response that already delivered can miss it and the wait hangs until the 30 s timeout (observed when a handler fires a burst of fetches and an earlier-registered sibling wait or prior assertions consume the window). Register all series waits in one `Promise.all` together with the click that triggers the requests; for re-open/re-render flows where the requests already fired, skip the response waits and let the retrying `expect` assertions wait on the rendered DOM instead. Likewise, when duplicating an SVG chart for a second metric give the new chart its own container class and share only the inner element classes — reusing the original container class makes strict-mode selectors like `#pricingPanel .token-chart svg` in the UI tests resolve to two elements.
- `npm run build` type-checks `test-node/**` and `scripts/**`; verify unrelated errors against clean source, apply the smallest type-only fix, and disclose it.
- Admin service methods are optional and routes register only when present. For a 404, compare `src/app/runtime.ts` wiring with `LogAdminService`, `PairAdminService`, and `SummaryModelAdminService`; add new-route coverage to the assembled-app smoke test in `test-node/app/runtime.test.ts`.
- UI modifications require screenshot verification. Clean temporary files and processes when done.
- After every task, build the portable executable: `npm run build && npm run rebuild:electron && npx electron-builder -w portable --publish never`.
- Native module ABI: run `npm rebuild better-sqlite3` only before the final `npm run rebuild:electron`; never run the Node rebuild after Electron rebuild or before packaging, or the portable app will contain a Node ABI binary and fail at startup.
- Execution history logs: `D:\Portable Program\llm_proxy\logs`.
- The portable exe is an NSIS wrapper around a 7z-compressed `win-unpacked` payload: raw string search in the `.exe` misses code; verify build contents in `release/win-unpacked/resources/app.asar` (or extract the 7z payload with 7-Zip). When an LLM Proxy instance is already running, do not assume it is your own test launch — the exe name and version are unchanged across consecutive same-version builds; check the process creation time and extraction path (portables unpack to a `Temp` dir) before querying or killing it, and only kill processes you started.
- Release: `npm version <patch|minor|major> --message "chore(release): %s"`, then push branch and tag (`git push origin main vX.Y.Z`). Publishing occurs only from `v*` tags; tag pushes rerun CI.
- CI without `gh`: query the public Actions REST API with `curl` (`/actions/runs`, details, `/jobs`). Job logs require a token (one is retrievable via `git credential fill`); diagnose `npm run check` by running `format:check`, `lint`, `typecheck`, `test`, and `build` separately. UI tests launch the Playwright-bundled Chromium (CI downloads it with `npx playwright install chromium`); never fall back to the OS Chrome, whose auto-updates on GH runners can hang `chromium.launch` (override with `CHROME_PATH` if needed).
- Portable exe build: `npm run build` + `rebuild:electron` + `electron-builder` totals ~30s. electron-builder compresses the 360MB win-unpacked with 7z `-mx=9` (ultra, ~100s) by default; `electron-builder.env` (auto-loaded by the electron-builder CLI, listed in .prettierignore) sets `ELECTRON_BUILDER_COMPRESSION_LEVEL=3` (~5s, exe grows only a few MB because most payload is already-compressed Chromium files). `win.electronLanguages` trims the 46MB locales dir to the wanted `.pak` files, but the matching is exact-per-locale: it must be `en-US`/`zh-CN`-style codes — a prefix like `en` or `zh` deletes ALL 55 locales and breaks the UI.
