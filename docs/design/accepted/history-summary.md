# 历史请求智能总结设计

> 状态：已接受设计
> 权威性：单请求总结的功能语义依据；执行过程内容合同引用任务执行过程设计。
> 更新条件：请求总结的输入、缓存、API 或交互变化时更新。

## 1. 决策摘要

单请求“智能总结”复用任务简介的事件输入、提示词、证据校验和弹窗组件，缓存仍以请求 ID 独立保存。

## 2. 需求

1. R1：选中请求使用 `prepareTaskTimelineInput(record)`，与任务简介使用同一个 `TASK_BRIEF_INSTRUCTION` 和版本；不改为读取该任务的最新请求。
2. R2：答案经过同一个时间线解析器，越界证据、非法顺序和缺失必需内容拒绝写入；失败保留原缓存。
3. R3：`history_summaries.summary_json` 保存校验后的时间线、环境信息、编号事件和来源元信息；无需数据库新增列。旧 `segments` 格式不转换，GET 返回空，用户手动重新生成。
4. R4：弹窗复用阶段渲染器及同一套弹窗样式，展示概述、环境、阶段位置轨道、目标、结果、思路、缺口与可跳转证据；目标展开，结果和思路以紧凑标题默认折叠。
5. R5：保留复制和重新生成；生成绑定点击时的请求，切换请求或关闭弹窗后迟到结果不得覆盖另一个请求或重新打开窗口；读取缓存不产生模型调用。

执行过程字段及公开推理边界以[任务执行过程设计](task-execution-summary.md)为唯一权威，本设计只规定请求级接入。

## 3. 接口与状态

`GET /api/logs/:id/summary` 返回新格式缓存或 `null`。`POST` 返回已校验并落库的总结；不存在的请求返回 404，同请求并发生成返回 409，不同请求独立执行。缓存按请求 ID 所属日志根保存，删除请求时沿现有外键级联删除。

新响应包含 `text`、`timeline`、`events`、`context`、`source_record_id`、`source_sequence`、`source_event_count`、`model`、`generated_at`。总结的证据是所选请求携带的历史上下文，不包含此次请求尚未写入输入的后续响应。旧缓存行保留，列表星标仍表示曾有成功生成记录；新界面遇到旧格式时手动生成新结果。

配置沿用 `summary_model`，不增加模型开关、后台任务或自动计费路径。实现权威为 `summary-generation-service.ts`；UI 通过共享时间线渲染函数接线。

## 4. 本轮非目标

不自动迁移旧摘要，不自动批量重新生成，不改变原始请求或响应，不增加流式总结或取消生成协议。
