## 1. 决策摘要

给目标加一个可选字段 `session_header`，值是一个 Header 名（例如 `x-opencode-session`）。配了它以后，代理在转发前保证这个头一定出现在请求里：客户端已经带了就不动，只带了自己的会话头就把值复制一份，什么都没有就按请求内容派生一个**同一会话恒定**的 id。留空就是不启用，今天的转发行为逐字节不变。

## 2. 背景

有的上游把“会话标识”当成硬性合同，不只是提示。OpenCode Go 现在就是这种上游：请求里没有任何会话头时直接 400 `MissingSessionID`（`Request is missing x-opencode-session and cannot be routed efficiently`），而这个头的作用是把同一段对话的路由和 prompt cache 粘在一起。

客户端不一定在每个请求路径上都记得发它。实测 pi 1.5.0 打 OpenCode Go 的 624 条历史记录里，主对话链路都带 `session_id` 且全部 200；上下文压缩走的是另一条自己拼 headers 的路径，一条会话头都不带，69 条全部 400（另 1 条被客户端中断）。也就是说请求被拒的原因不是压缩本身，而是那条路径上没有会话标识。代理已经把请求体完整收在内存里（压缩请求体里就带着整段会话），有条件在转发前补齐。

## 4. v1 明确不做

- 不改 pi 或任何客户端：它们的漏头是它们的问题，代理只补自己转发出去的那一份。
- 不按域名自动识别 OpenCode Go：自动魔法会让“为什么这个目标多了个头”无法解释，启用是显式的用户决定。
- 不给 `summary_model` 加同一个字段：那是控制台自己的调用配置，与目标配置是两套合同，等有人需要时单独立项。
- 不覆盖客户端已经带来的值，也不伪造客户端身份（`user-agent`、`x-opencode-client`）：本功能只补齐“缺失的会话标识”，不做客户端冒充。
- 不做“把压缩请求匹配回主对话的会话 id”的模糊搜索：需要在几百 KB 的请求体上做跨记录匹配，代价和误判都不值得，见第 7 节。

## 5. 字段与取值

```ts
// src/config/config-schema.ts（targetConfigSchema）
session_header: z.string().trim().max(64).default("");
```

- `""`：关闭，转发集合与今天一致。
- 合法值：`/^[A-Za-z0-9!#$%&'*+.^_`|~-]+$/`，且不在禁止集合（hop-by-hop 头、`host`、`content-length`）里。

取值来源顺序（启用且转发集合里没有这个头时）：

| 顺序 | 来源                                                             | 值                                                                                          |
| ---- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1    | 客户端已有的同名头                                               | 原样（R2，实际是“不动”）                                                                    |
| 2    | `session_id` → `x-session-affinity` → `x-claude-code-session-id` | 第一个非空值，去掉首尾空白                                                                  |
| 3    | 请求内容派生                                                     | `proxy-` + `stableHash({kind, model, 边界指纹去 first_user, 首条用户文本前 4096 字符}, 24)` |
| 4    | 内容也取不到                                                     | `proxy-` + `stableHash({kind, path}, 24)`                                                   |

派生 id 的稳定性（R4 的验收口径）：

| 场景                                            | 结果                                                                                                                               |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 同一会话连续三轮，客户端都没带会话头            | 三个值相同（`model`、`system`/`instructions`、首条用户消息都不变）                                                                 |
| 同一会话的两次压缩请求（首条用户文本超过 4 KB） | 两个值相同（压缩体以整段会话开头，前 4096 字符不变）                                                                               |
| 首条用户文本不足 4 KB 时的两次压缩请求          | 值可能不同：整个短会话都是证据，会话一长超出窗口就变了。真正会触发压缩的会话远超这个长度，所以这只是小会话上的一次多分桶，不是错误 |
| 两个不同会话                                    | 值不同（首条用户文本不同）                                                                                                         |
| 会话被压缩后重新开始                            | 值变化：历史被摘要替换，首条用户文本变了。这是一次性的分桶边界，不是缺陷                                                           |

## 6. UI 合同

- 位置：目标卡片 →“更多目标选项”→ 与“上游 Headers / 剥离字段 / 注入字段”并列的一个文本输入框。
- 留空即关闭；输入即启用，占位提示给 `x-opencode-session`。
- 非法头名（含空格、冒号、非法字符）在保存时按 `invalid_config` 拒绝并指出字段路径，不静默丢弃。

## 7. 已知取舍

压缩请求的派生 id 与主对话的会话 id 不是同一个值：主对话那一侧代理复制的是客户端自己的 `session_id`，压缩请求那一侧没有任何客户端会话证据，只能按内容派生。结果是压缩那一次请求换了一个路由桶，吃不到主对话的 prompt cache。要让两者对齐，需要在几百 KB 的请求体里把压缩请求模糊匹配回主对话的记录，误判会把不相干的会话粘到一起（比一次冷启动更贵），因此 v1 明确不做。

## 9. 开放问题

| 问题                                              | 推荐                                    | 替代方案                                    | 对 v1 的影响                                     |
| ------------------------------------------------- | --------------------------------------- | ------------------------------------------- | ------------------------------------------------ |
| `session_header` 该不该也支持 `Name: 固定值` 写法 | v1 只收头名，值由代理决定               | 允许 `Name: value`，等价于 `target_headers` | 两种写法表达同一件事会让“谁优先”变成新合同，暂缓 |
| 要不要把派生 id 落盘以便重启后继续同桶            | v1 不落盘，派生是纯函数，重启后自然一致 | 写入 runtime 状态文件                       | 纯函数已经满足“重启后同会话同值”，落盘只增加状态 |
| 压缩请求是否需要对齐主对话的桶                    | v1 不对齐                               | 基于内容模糊匹配回主对话                    | 见第 7 节，误判代价高于收益                      |
