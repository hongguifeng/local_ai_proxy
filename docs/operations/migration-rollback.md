# 数据迁移与回滚

> 状态：运维手册
> 权威性：Node/Electron 版本升级、配置迁移和 traffic database 回滚操作。
> 更新条件：schema 版本、备份流程、配置格式或交付脚本变化时更新。

所有操作先复制数据，再在副本上演练。不要对用户正在运行的实例执行迁移，也不要覆盖原始 `traffic.db` 或 `proxies.json`。

## 迁移前

1. 关闭你自己启动的隔离实例，等待所有监听端口关闭，确认没有其他进程写入副本。
2. 复制 `llm-proxy.json`、`logs/proxies.json` 和每个日志根的 `traffic.db`；若存在 `traffic.db-wal`、`traffic.db-shm`，在 SQLite 连接关闭后一起复制。备份目录使用 `before-node` 标记。
3. 记录当前应用版本、Node ABI、Electron ABI、数据库 schema 版本、pair 数量、task/record 数量和孤儿关联数。
4. 用 `npm run abi:node` 或 `npm run abi:electron` 证明将要使用的绑定。

## 运行迁移

在副本上使用项目的迁移入口或 `npm run rehearse:real-data`，不要手写 SQL 改生产库。迁移应先备份，再按 schema 版本顺序执行，在事务内校验表、索引、正文分块、FTS 和外键关系。需要检查历史副本时运行 `npm run validate:migration`，不要把以前接受的版本的验收记录当成当前副本已经验证。

校验至少包括：

- 旧配置能打开，未知键没有消失。
- 所有预期表、索引和 schema 版本存在。
- task、record、context link、response link 的数量和关系可解释。
- 正文读取、搜索、导出和统计仍能工作。
- 迁移后副本可以由当前 Node 进程重新打开。

## 仅回滚配置

停止隔离实例，把当前配置文件改名保存，再将迁移前备份恢复到原位置。重新启动时先运行配置校验；如果 pair 的监听端口或日志根发生变化，确认新实例使用的是隔离端口和日志目录。

## 回滚配置和数据库

停止写入后同时恢复配置和 `traffic.db`。不要只恢复数据库而继续使用新配置，因为 target、日志根和价格规则可能不再对应。恢复后重新执行数量、正文、搜索和健康接口检查，再决定是否启动代理。

## 失败处理

迁移脚本失败时保留原始副本、备份、副本日志和完整错误，不要重复覆盖同一个副本。若怀疑原生模块 ABI，先用真实查询确认；若怀疑 SQLite 锁，检查是否仍有自己启动的进程持有连接。用户实例保持运行时只能读，不能为了复现而停止它。
