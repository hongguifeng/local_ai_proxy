# 管理端 UI 两次模型对照开发记录

> 状态：报告
> 权威性：两次独立模型开发实验的过程、测量和验收证据。
> 更新条件：补充同一实验任务的复验结果，不把本报告中的一次性数字改写成当前产品性能合同。

## 实验范围

本报告记录两次管理端 UI 任务的模型对照开发。每次任务都交给 `qwen3.8-27b` 和 `Qwen3.8-Flash-Next`，两个模型使用独立 worktree，收到相同任务说明，统一使用 `xhigh` 思考强度。实现完成后由主会话独立 review、选择和验证；模型自报的结果不直接视为验收结论。

执行窗口为每个 child `7200000ms`，并在截止前 `600000ms` 创建 checkpoint。第一次拖动排序实验的初始委派错误使用了 30 分钟窗口，两个 child 都曾因超时中断，之后从 checkpoint 恢复到两小时窗口；这属于编排窗口错误，不能作为模型能力差异。第二次 JSON 性能实验直接使用两小时窗口。

两个任务都遵守以下边界：不修改主 worktree，不停止或改写用户正在运行的实例，不写用户配置或 `traffic.db`，不在独立 worktree 执行 Electron packaging。最终选择的实现才在主 worktree 运行完整交付链。

## 任务一：Target 卡片拖动排序

### 任务和验收标准

目标是修复管理端“转发地址 / Target 卡片”的 pointer 拖动排序，使卡片落在鼠标指针对应的视觉位置，同时保持 pointer events、键盘排序、保存顺序、`data-target-index` 映射和现有 UI 合同。

验收覆盖横向网格、卡片间隙、不同卡片高度、换行网格、窄屏单列、拖动自身区域、滚动容器、键盘排序和配置保存。

### 两份实现

`qwen3.8-27b` 的提交为 `3676649`。它把旧的“最近卡片加中点”逻辑改成两阶段判断：先根据垂直带选择视觉行，再根据该行的布局轴比较卡片中点。它新增了 6 个浏览器测试，并更新了 `ui-markup-contracts` skill。

这个方案能修复原算法的主要错误，特别是二维距离判断在间隙、换行和不同高度卡片下的错误落位。它仍然依赖“先选行、再比较行内中点”的布局假设，没有处理 Chromium 滚动锚定导致的拖动偏移。

`Qwen3.8-Flash-Next` 的提交为 `37d5455`。它把卡片边界扩展到相邻卡片边界的中点，形成明确的视觉插槽，由指针所在插槽直接决定插入位置。它还增加了：

- `body.drag-target-active .proxy-view { overflow-anchor: none; }`，避免 DOM 重排触发浏览器滚动补偿；
- 间隙、不同高度、换行、窄屏、自身区域、滚动容器和保存顺序测试；
- 7 个新增浏览器场景和对应的 UI 合同说明。

### Review 结论

这一任务采用 Flash 方案。主要依据是它的几何模型更直接地表达了用户要求，覆盖的边界更多，并修复了 27B 没有处理的滚动锚定问题。这里的选择主要由算法模型、测试覆盖和实际交互风险决定；本次没有为两份拖动实现建立同一套数值性能基准，因此不能据此宣称某个模型的拖动代码运行更快。

最终主分支提交为 `556d9ac`。主分支验收结果为：

- `npm run check`：151 个测试文件通过、1 个跳过；1635 个测试通过、2 个跳过；
- 拖动相关 `admin-ui-proxy.test.ts`：40/40 通过；
- UI 视觉测试：11/11 通过；
- `npm run check:skills`：8/8 通过；
- 文档测试：37/37 通过；
- `npm run package:electron:portable`：通过；
- payload 和 portable wrapper 冒烟：健康检查、代理请求 200、日志 API 200、真实 `traffic.db` 创建成功；
- Node ABI 恢复和真实 SQLite 查询：通过。

## 任务二：历史日志 JSON 请求显示性能

### 任务和验收标准

目标是优化历史日志界面的 JSON 请求显示，重点解决大请求体首次显示慢、展开和滚动卡顿，以及请求仍在进行时自动刷新造成的卡顿或内容迟迟不完整。

要求保持 JSON 内容、格式化、懒加载、展开/收起、展开一层、复制、换行模式、滚动位置、请求切换竞态、自动刷新和已有 UI 合同。

### 27B 的实现和证据

`qwen3.8-27b` 的提交为 `996438d`。它定位到的主要根因是：每次 `preserveView` 刷新都会执行 `collectJsonPaneViewState()`，遍历所有 JSON 详情节点，并读取字符串 body 的滚动属性；关闭状态的大文本也会因此触发布局。模型在约 6MB 请求体和增长中的响应上测得一次约 3.7–3.8 秒的布局冻结，热页面刷新也出现过约 180–460ms 的帧间隙。

它的修复包括：

- 未变化的 render input 跳过 JSON 树构建、DOM 解析和视图状态遍历；
- 只有真正替换 DOM 时才收集展开状态和滚动位置；
- 只读取打开的长字符串 body 的滚动位置；
- 把 materialization 的文本测量范围限制在当前节点；
- 重新选择同一条记录时用 `force` 真正恢复初始视图。

它的改动规模为 5 个文件、277 行变更。新增测试证明大 JSON in-flight 刷新不触碰未变化的 request pane，没有超过 100ms 的帧间隙，也没有 long task；响应增长后最终内容完整显示。

### Flash Next 的实现和证据

`Qwen3.8-Flash-Next` 的提交为 `5cdb412`。它没有把整棵树作为一个整体重建，而是为已经渲染的 row 保存原始值，通过 `data-json-child-key` 对 JSON 子节点做增删、移动和局部替换：

- 未变化的子树保持原 DOM、展开状态和已 materialize 的内容；
- 单叶子变化只替换对应 row；
- 新增和删除的 key 只修改对应子节点；
- key 顺序变化移动既有 row，而不是重建全部内容；
- lazy 填充、节点替换和队列异常恢复都有对应处理。

它的改动规模为 5 个文件、1003 行变更。开发过程中曾发现并修复旧文本残留、替换节点被重新插回、mutation 数量过多、JSDoc 类型错误和 key 顺序被冻结等问题。最终新增 4 个专门的 JSON refresh 性能/行为测试，并通过了 50/50 的历史相关定向测试。

### 同口径性能复测

最初选择 27B 时没有在两个方案上运行同一个 A/B 基准。经过复核后，使用同一份临时 Playwright/Vitest 测试分别在两个 worktree 运行。该临时测试执行后已删除，因此这里保存的是实验结果，不是可执行的长期性能门禁。

测试输入和步骤完全相同：

- 2500 条消息；
- request 约 6MB；
- response 从 750KB 增长到 1.5MB；
- 连续执行 4 次进行中刷新；
- 测量同步刷新时间、下一帧时间、long task、DOM 行数和最终响应尾部。

结果如下：

| 指标              |    27B | Flash Next |
| ----------------- | -----: | ---------: |
| 最大同步刷新耗时  | 31.8ms |     15.9ms |
| 最大下一帧延迟    | 48.9ms |     28.9ms |
| long task         |      0 |          0 |
| request 行数      |   2505 |       2505 |
| response 完整显示 |   通过 |       通过 |

这组数据表明，在该大 JSON、进行中刷新场景下，Flash 的同步工作量和下一帧延迟约为 27B 的一半。两份方案都没有出现长任务，性能差异来自 Flash 更细粒度的节点复用，而不只是“一个通过、一个失败”。这组结果只代表该输入规模和当前 Chromium 测试环境，不代表所有数据形状下的普遍性能比例。

### Review 结论

在看到同口径 A/B 数据之前，主分支曾短暂合入 27B 的 `0f14576`。复核后使用 `b51665d` 明确回退该提交，再合入 Flash 方案，最终提交为 `fb8a1b3`。

采用 Flash 的依据是：

1. 它在受控基准中实际更快；
2. 它的最终测试已覆盖之前发现的 stale DOM、节点替换和 key 顺序问题；
3. 它在完整 UI 测试和交付验证中通过；
4. 它的复杂度是可见的维护成本，但不再只是没有数据支持的复杂度担忧。

- 新增 JSON refresh 性能测试：4/4 通过；
- `npm run check:skills`：8/8 通过；
- 文档测试：37/37 通过；
- `npm run package:electron:portable`：通过；
- payload 和 portable wrapper 冒烟：健康检查、代理请求 200、日志 API 200、真实 `traffic.db` 创建成功；

### 后续修复：切换记录时重置 JSON 视图

交付复核发现，Flash 方案虽然已进入 bundle，但 `selectLog()` 传入的 `resetView` 没有继续传给请求和响应 JSON pane。结果是切换历史记录时，reconcile 会复用上一条记录的树和展开状态；在大 JSON 上还会把旧树与新数据做同步，造成额外的切换工作。主 worktree 以 `685ff5f` 修复了透传，并新增测试确认旧节点已从 DOM 移除、新记录的深层节点恢复折叠。

修复后的 `npm run check` 结果为 152 个测试文件通过、1 个跳过；1642 个测试通过、2 个跳过；历史相关测试为 47/47。修复后的 portable 交付链、payload 和 wrapper 冒烟、`app.asar` 内容检查以及 Node ABI 恢复均通过。此次补充只记录当前交付修复和验证结果，不改变前面受控 A/B 基准的范围。

### 后续修复：滚动后展开大 JSON 节点

复核发现，lazy materialization 虽然已经按节点进入任务队列，但单个节点内部仍会一次性生成全部子行；当用户滚动后展开一个拥有大量子项的节点时，DOM 插入和尺寸计算会占满下一帧。主 worktree 现在把单节点 materialization 分成每批 96 行、每个任务约 12 ms 的队列，节点先打开，剩余子行由后续任务补齐。新增测试覆盖滚动后展开 402 个子行和重新展开 2500 个条目的大数组。

专项测量中，滚动后展开的同步点击工作约 0.2 ms，最大帧间隔约 16.8 ms，402 个子行最终完整出现。

## 综合表现对比

| 维度         | `qwen3.8-27b`                                                | `Qwen3.8-Flash-Next`                                              |
| ------------ | ------------------------------------------------------------ | ----------------------------------------------------------------- |
| 任务理解     | 能沿着现有实现定位问题并补齐合同                             | 更倾向于重新建模交互或渲染问题                                    |
| 根因分析     | 拖动任务中采用两阶段行/中点模型；JSON 任务中准确定位强制布局 | 拖动任务中建立插槽模型；JSON 任务中识别 line-count 和整树协调成本 |
| 实现取向     | 在现有结构上做较小范围修复                                   | 用更完整的几何或节点协调模型替换旧路径                            |
| 改动规模     | 两次任务都较小                                               | 两次任务通常更大，JSON 任务尤其明显                               |
| 测试质量     | 能补充针对根因的回归测试                                     | 更倾向于补充可观察性能、DOM 复用和边界行为测试                    |
| 主要风险     | 可能保留旧模型的隐含假设；JSON 方案仍有完整 raw 序列化成本   | 实现状态多，开发过程中更容易出现节点复用和 stale DOM 错误         |
| 本次最终采用 | 未采用拖动和 JSON 两个任务的最终方案                         | 两个任务的最终方案都采用                                          |

这两次实验支持的结论是有限的：Flash Next 在本项目的两类浏览器 UI 任务中更容易提出覆盖面更大的模型，并在第二个任务的同口径基准中取得更低刷新延迟；27B 更擅长沿现有代码路径做集中、低风险修复。样本只有两个任务，且两个任务都属于管理端 UI，不能据此推断两个模型在所有软件开发任务上的普遍能力排序。
