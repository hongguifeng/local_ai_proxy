# 历史请求智能总结设计

## 1. 背景与目标

历史详情目前以完整 JSON 展示请求内容。多轮对话会导致 JSON 体积快速增长，阅读者难以按时间顺序理解对话流程。本功能允许用户为管理端配置一个“总结模型”，在历史详情标题栏点击按钮后，将该 record 的对话内容按原始顺序提取并发送给指定模型，返回结构化、精简的流程总结，并在详情页展示。

目标是：不改变原始日志；总结可重复生成、可追溯；失败时不影响历史浏览；对超长上下文有明确限制和提示。

## 2. 方案概览

推荐采用“显式生成 + 缓存结果”方案：

1. 全局配置增加 `summary_model`；只要配置存在即启用，包含 API 类型、URL、API Key、模型名、可选 headers 和超时。
2. 标题栏增加“智能总结”按钮。点击后管理端读取该 record 的完整对话数组，按原始数组顺序，转换为统一的事件列表。
3. 管理端调用配置的上游总结模型，要求其只返回约定 JSON；服务端校验并保存结果。
4. UI 在请求 JSON 旁显示总结卡片，可折叠、复制、重新生成；已有结果默认直接展示，避免重复计费。

总结输入压缩规则：保留原始消息/输入项的顺序，以及工具调用的 `type`、`call_id`、名称和参数；保留工具结果但对结果正文做长度截断。不得仅保留工具名称或删除 `function_call` / `function_call_output`，否则总结模型无法建立调用与结果之间的因果关系。

相比浏览器直连模型，该方案可保护 API Key、统一超时和重试，并能在数据库中保留生成时使用的模型快照。

## 3. 配置设计

在 `ProxyConfigFile` 增加可选全局字段（旧配置缺省为空）：

```json
{
  "summary_model": {
    "api_type": "openai_chat",
    "target_url": "https://api.example.com/v1",
    "api_key": "...",
    "model": "gpt-5.6-sol",
    "target_headers": [],
    "timeout_ms": 180000
  }
}
```

支持现有 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 三种协议；复用 target-check 的请求构造和错误处理。保存配置时校验 URL、模型、超时范围和 headers。

## 4. 数据模型与 API

新增 SQLite 表 `history_summaries`：`record_id` 主键、`status`、`summary_json`、`source_hash`、`model`、`prompt_version`、`created_at`、`updated_at`、`error_message`。删除 task 时级联删除；原始 request/response 字段不变。

新增管理 API：

- `GET /api/settings/summary-model`：读取配置。
- `PUT /api/settings/summary-model`：校验并保存配置。
- `GET /api/logs/:id/summary`：返回缓存结果及状态。
- `POST /api/logs/:id/summary`：触发生成；正在生成返回 202，重复点击返回 409 或复用进行中的任务。

生成接口建议返回 `{status:"ready", summary, generated_at, model}`；失败返回可读错误，不返回上游密钥或完整请求体。

## 5. 输入整理与提示词

服务端只发送必要字段：消息序号、时间、角色、模型、文本内容、工具调用名称/结果摘要、状态和耗时。工具调用参数、二进制内容和大段工具输出会被移除或截断，只保留短预览。先按原始顺序编号，再要求模型把连续编号合并为若干“阶段区间”，不逐条复述每句话；只有关键决策、异常和转折点才引用具体编号。超过输入 token 配额时按消息边界截断，并标记 `[已截断]`。

系统提示词要求模型按编号顺序，把连续消息合并为若干阶段区间，不逐条复述；仅保留关键决策、异常和转折点的证据编号，并严格返回：

```json
{"title":"...","overview":"...","segments":[{"range":"1-10","summary":"建立上下文并确认目标","key_points":["确认输入约束"],"evidence":[1,4,10]}],"decisions":["..."],"issues":["..."]}
``` 

例如 24 条消息可归纳为：`1-6` 收集背景并确认任务；`7-12` 分析现状并发现配置问题；`13-18` 提出和比较实现方案；`19-22` 根据反馈修改方案；`23-24` 给出结论和后续动作。只有关键节点（如第 14 条鉴权失败、第 20 条范围调整）引用证据编号。

服务端对 JSON 做 schema 校验；解析失败可进行一次“仅修复 JSON”重试，仍失败则标记失败并保留错误原因。

## 6. UI 交互

在“历史日志”页面列表上方的操作按钮中增加“总结模型配置”按钮。点击后打开类似转发地址“测试”功能的模态弹窗，包含 API 类型、Base URL、模型名、API Key、可选 Headers 和超时（默认 180 秒）；配置按钮旁可显示“未配置/已配置”状态。总结输入不设置 token 数上限。

在历史详情标题栏放置“智能总结”按钮：无配置时置灰并提示前往设置；生成中显示 spinner 和“取消/后台运行”状态；完成后在详情顶部显示标题、概览、步骤时间线、决策和问题列表。提供“重新生成”“复制 Markdown”“查看生成信息”操作。切换请求或刷新页面不丢失状态，轮询 `GET summary` 或使用现有刷新机制获取完成结果。历史列表的二级列表（任务下的请求项）中，已生成总结的请求在时间之后、状态之前显示金色星标（★），悬停提示“已生成智能总结”；列表项由服务端查询 `history_summaries.status = 'ready'` 返回 `has_summary` 标记，生成或打开已有总结后前端同步刷新标记。时间、星标、状态均左对齐，星标不影响状态位置。

## 7. 安全、成本与可靠性

未配置时总结模型不可用，配置存在即启用；总结输入遵循现有日志内容处理规则且不限制 token 数。API Key 按现有管理工具方式保存，错误日志不得包含 prompt。限制并发生成数（建议 1）、超时和响应大小；对相同 `record_id + source_hash + prompt_version` 使用缓存。用户明确点击才产生费用，并在 UI 展示模型和生成时间。

## 8. 分阶段实施与验证

阶段一：配置 schema、设置 API、SQLite 迁移和纯服务端 prompt/解析模块。

阶段二：生成 API、并发/超时/失败处理、删除 task 联动。

阶段三：历史标题栏按钮、总结卡片、轮询和复制功能；更新中英文 README，并运行 `npm run regen:ui-baselines` 更新 UI 基线截图。

验证覆盖：三种 API 协议、空 task、超长 task、截断、多次点击、上游 4xx/超时、无效 JSON、配置脱敏、task 删除和旧数据库迁移。补充 admin API 与 UI 测试，确认原始 JSON 展示和导出行为保持不变。

## 9. 后续可选增强

可增加“只总结当前选中请求”“自定义总结风格/语言”“流式显示步骤”和本地模型优先级。第一版不建议自动总结全部历史，以免产生不可控费用和后台负载。
