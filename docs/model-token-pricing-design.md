# 转发地址模型定价与历史费用设计

状态：待评审，尚未实现。日期：2026-09-11。

## 1. 目标与推荐决策

每个转发地址可以配置多条模型价格规则，支持精确模型名与 `*` 通配符。历史记录的二级请求行显示单次费用，一级 task 行显示整个任务的费用合计。

建议首版采用以下规则：

| 项目 | 推荐设计 |
| --- | --- |
| 价格归属 | 属于具体 target，以 proxy pair ID + target ID 定位；相同 URL 的两个配置可使用不同价格 |
| 币种与单位 | 固定人民币，所有单价均为元 / 1,000,000 token |
| 价格与倍率 | 普通输入、输出、缓存读取、缓存写入分别计费；每条规则的倍率乘到四项价格，所得实际单价用于计费与历史展示 |
| 匹配对象 | 完成模型映射、字段删除和注入后，实际发往上游请求中的 `model` |
| 匹配顺序 | 精确匹配优先；没有精确匹配时，通配规则按界面从上到下取第一条 |
| 价格生效 | 请求准备转发时冻结价格，新配置只影响后续请求 |
| 历史日志 | 已计费记录保留当时单价；升级前记录显示“未计价”，首版不自动补算 |
| 不完整信息 | 缺价格或缺 usage 不视为零元；task 列表只显示已知金额合计，未计价/进行中数量只在费用明细面板显示 |
| task 合计 | 汇总该 task 全部已保存请求，与分页、折叠和搜索关键词无关 |
| task 地址边界 | 一个 task 只对应一个转发地址；不同转发地址会新开 task，沿用现有分组行为 |
| 金额展示 | 最多 4 位小数，四舍五入后去掉末尾零；内部计算和存储保留精度 |
| task 头部 | 三行且每行不换行：日期时间；模型、请求数、可点击费用；转发地址。宽度不足时裁切 |

本功能提供根据手动单价和上游 usage 计算的费用估算，不接入供应商账单。首版不包括汇率、多币种、阶梯价格、按缓存 TTL 分档、工具调用固定费、自动同步价格或预算告警。

## 3. UI 设计

### 3.1 转发地址卡片

在“模型映射”下面增加独立折叠区“模型价格 · N 条规则”。不放进现有“更多选项”，保证功能容易发现，同时避免每个 target 都出现大表格。

```text
转发地址 A                                      [测试] [删除]
转发地址  https://api.example.com/v1
API Key   ••••••••••
模型映射  sol => gpt-5.6-sol

▾ 模型价格 · 2 条规则                        [+ 添加模型价格]
  单位：元 / M token（100 万 token）
  按实际转发模型匹配；精确匹配优先，通配规则从上到下匹配。

  模型名称 / 通配符   普通输入  输出   缓存读取  缓存写入    操作
  gpt-5.6-sol         5         30     0.5       6.25        ↑ ↓ 删除
  gpt-5.6-*          5         30     0.5       6.25        ↑ ↓ 删除

  测试模型名 [gpt-5.6-sol-preview             ]
  命中第 2 条：gpt-5.6-* · 输入 5 / 输出 30 / 读 0.5 / 写 6.25

  修改价格后，后续请求使用新价格，历史费用保持原值。
```

上面的第二条价格仅用于演示通配规则，不表示其他模型的实际价格。

交互细节：

- 新建 target 默认无规则，空态提示“尚未配置模型价格，请求费用将显示为未计价”。
- 添加时展开价格区，聚焦模型输入框。模型名与四项价格必须填写；倍率默认为 `1`；允许显式填写 `0` 表示免费，空白不等于零。
- 使用普通十进制文本输入与 `inputmode="decimal"`，支持粘贴，避免浏览器数字输入框默许科学计数法。
- 配置单价和倍率均为非负、最多 6 位小数、最高 1,000,000；超出时标红并阻止保存，不静默截断。
- 模型名去除首尾空格后不能为空；同一 target 内完全相同的 pattern 不允许重复。
- ↑/↓ 调整通配规则优先级；精确规则无论位置始终优先。`*` 可作为最后一条兜底规则。
- 测试框直接使用当前未保存规则，不发送上游请求；显示命中的原始行号、模式和价格。保存时后端仍是最终校验权威。
- 所有修改随现有配置保存操作统一生效；添加、删除或测试本身不提前保存。重绘前保留各输入值和焦点。
- 窄 target 卡片中每条规则切换成“模型整行 + 倍率与四个价格两列”的布局；无需把整个配置页横向撑宽。
- 中英文均使用相同含义的字段和帮助文本，人民币不会因切换英文而变为美元。

### 3.2 历史记录一级：task 费用

分组头部改为三行布局，转发地址独占第三行，不再与金额竞争宽度：

- 第一行：保持现有日期、时间格式与布局，信息内容仅为日期和时间，不放请求数。选择框和展开箭头保持原有操作位置。
- 第二行：依次显示模型、请求数、费用（含必要的计价状态）。直接点击费用进入 task 明细，不增加独立“费用明细”按钮。
- 第三行：转发地址，独占一行。

历史一级和二级列表的每个显示行都禁止自动换行；宽度不足时允许右侧内容被裁切、显示不完整，不通过换行增加高度，也不为费用强行压缩或重排其他信息。一级每行使用 `white-space: nowrap`、`overflow: hidden`，横向布局禁止 flex wrap，按容器边界裁切；二级保留现有指标列的截断方式。这里的禁止换行针对列表，不改变配置表单与请求正文查看器的布局。

一个 task 只对应一个转发地址，不同转发地址会新开 task。第三行直接使用现有 task 摘要中的 `target` 显示地址，超宽部分裁切，无地址时显示 `—`。

```text
  https://api.example.com/very/long/upstream/path/v1
    #1   请求       响应       费用
         3000       1000       ¥0.0411
         14:20:10 · 200
    #2   请求       响应       费用
         1000       25         ¥0.0013
         14:22:05 · 200
    #3   请求       响应       费用
         750        0          ¥0.0004
         14:26:00 · 200

▸ 09-11 15:00–15:03
  gpt-5.6-sol    4 个请求    ¥0.0428
  https://api.example.com/v1
```

线框中的日期时间仅示意内容，实际保持现有格式；费用文字本身可点击。二级沿用现有“请求”“响应”标签和下方数字，原有“条消息”列在有数据时仍保留，示例省略该列。示例 #2、#3 输入均全部命中缓存读取；#1 的四类明细见下一节。“请求”token 仍表示包含缓存的总输入，费用详情负责解释分项。

一级只显示金额：始终显示该 task 已知金额合计（未计价/进行中不计入），没有任何已计价请求时显示 `—`；已知、未计价、进行中的数量与原因在费用明细面板中展示。

搜索模式下仍显示 task 全额，在费用明细面板中附注“整个任务费用，包含未匹配请求”，不额外增加列表行。同一 task 的转发地址固定，但各请求可能使用不同价格快照，因此仍逐请求计算后汇总，不能用当前单价推算总额。

### 3.3 task 费用明细

第二行的费用文字就是明细入口，使用无边框的文本按钮样式，hover/focus 时提示可交互，辅助名称为“查看任务费用明细”，不增加额外可见按钮或图标。即使 task 未展开、全部未计价或正在计算，其费用占位文字也可点击。点击后在现有详情区域显示 task 费用面板，与单请求详情共用空间；不会切换请求列表的展开状态。分组头部使用容器组织独立交互元素，不能在现有大按钮中嵌套按钮；选择框、展开操作和费用文本分别响应键盘与点击，点击费用不冒泡触发展开或选择。

```text

¥0.0428                       已计价 3 / 未计价 0 / 进行中 0
转发地址：https://api.example.com/very/long/upstream/path/v1

普通输入                 1,500                        0.0075       17.54%

缓存读取                 2,750                        0.0014        3.27%
缓存写入                   500                        0.0031        7.18%
合计                                                  0.0428         100%

按模型 / 单价分组（默认展开，面板刷新后恢复展开）
▾ gpt-5.6-sol · 3 次请求                             ¥0.0428
  类别         已计价 token 数      单价（元/M token）   金额（元）   占比
  普通输入         1,500                 5               0.0075     17.54%
  输出             1,025                30               0.0308     72.01%
  缓存读取         2,750                0.5              0.0014      3.27%
  缓存写入          500                6.25              0.0031      7.18%

```

面板顶部显示该 task 的转发地址，上半部分汇总四类 token 与费用，下半部分按“实际模型 + 乘后四项实际单价 + 算法版本”分组，每组默认展开，表格内直接列出四类实际单价。面板数据刷新后重新渲染，展开状态恢复为默认展开；用户手动折叠只在当前展示期间生效。地址是 task 的共同属性，不作为组内分组维度。同一模型在任务期间改过价或倍率时拆成不同价格组，不能用当前单价乘整个 task 的 token，也不展示一个混合平均单价。单纯计价时间不同不拆组。

总额、四类明细与分组小计都从该 task 全部记录的原始计费数据计算，与请求列表分页、搜索词无关。四类 token 仅统计完整已计价请求，标明“已计价 token 数”，不让缺价请求的 token 与已知费用混在一起。未计价记录按原因统计数量，进行中单列。全未计价时显示原因分布，不显示假的零元明细。

面板说明“各项独立舍入，显示值相加可能存在尾差；合计按原始精度汇总”。请求完成、归组变化或清理记录后刷新已打开的 task 面板；任务被删除时显示“任务已删除”，清除旧金额。

### 3.4 历史记录二级：请求费用与明细

保留当前 `logItemMetricsHtml()` / `logMetricHtml()` 的指标布局：每列标签在上、数字在下。现有“条消息”“请求”“响应”的文案、数值格式、顺序、分隔线和时间/状态子行均保持原样；仅在指标区末尾追加同样格式的“费用”列，上方显示“费用”，下方显示金额。不要改成“输入 3,000 / 输出 1,000”这样的标签数值同行布局，也不要新增单独的费用行。

费用列沿用现有指标字号、间距及数值样式，每个标签/数值行保持单行，宽度不足时裁切，不让指标列折到下一排。各指标列不整体隐藏，而是随可用空间减少逐列被压缩裁切，裁切顺序从右向左：先费用、再响应、最后请求，条消息列保持完整。未知金额下方数值显示 `—`，进行中显示 `计算中…`；“无匹配价格”“缺少用量”等具体原因在请求详情及提示中说明，不在列表另加一行。点击请求仍按现有方式打开请求详情，不需要在二级费用列内再加独立按钮。

一级、二级、task 明细和请求明细的费用金额统一最多显示 4 位小数，按十进制四舍五入后去掉末尾零及多余小数点。例如 `5.0000 → ¥5`、`0.0300 → ¥0.03`、`0.041125 → ¥0.0411`、`0.042750 → ¥0.0428`。正数小于 `0.0001` 时显示 `< ¥0.0001`，零显示 `¥0`，未知显示 `—`。金额格式化使用整数/十进制字符串运算，避免浮点导致临界值舍入错误。

4 位限制作用于费用展示，数据库、API 和导出仍保留原始精度；配置单价与倍率最多 6 位小数，快照单价保留相乘后最多 12 位小数，并且只暴露实际单价。一级汇总按存储精度计算，不对已经显示的金额求和。

点击请求后，响应工具栏的 **¥** 按钮与元信息按钮一致，默认不展开费用明细；有计价信息时点击该按钮即可显示或隐藏现有请求/响应详情区中的费用明细，不另开弹窗：

```text
费用估算                                         ¥0.0411
计价模型：gpt-5.6-sol     命中规则：gpt-5.6-sol
价格来源：转发地址 A · 请求转发时价格

类别         token 数       单价（元/M token）       金额（元）       占比
普通输入       1,500             5                    0.0075       18.24%
输出           1,000            30                    0.03         72.95%
缓存读取         1,000             0.5                  0.0005        1.22%
缓存写入         500             6.25                 0.0031         7.6%
合计                                              0.0411       100%
```

此明细总输入为 3,000 token，与上方列表示例 #1 一致；两处使用同一标准化结果。

详情还展示计价时间、使用的四项实际单价快照、usage 来源和无法计价的原因。帮助文本说明“金额根据配置价格及上游返回的 token 用量估算”。不能仅依靠 hover 提供状态，键盘和触屏也应能查看。

## 4. 模型匹配与价格快照

### 4.1 匹配语义

复用 `modelPatternMatches(pattern, model)`，只将 `*` 解释为任意长度字符串（可以为空）。大小写敏感，匹配完整模型名；`?`、方括号等不是特殊语法。

算法：先在选中 target 的规则中找无 `*` 的精确项；没有精确项，再按数组顺序查找第一个匹配的通配项。没有命中就未计价，不借用其他 target 的价格，也不隐式套用默认模型价格。

例：规则顺序为 `*`、`gpt-5.6-sol`、`gpt-5.6-*` 时，`gpt-5.6-sol` 仍命中精确项，但 `gpt-5.6-sol-preview` 命中最前面的 `*`。界面建议把兜底规则放最后，并提供测试框验证重叠规则。

### 4.2 使用哪个模型名

价格匹配读取最终上游请求体：

```text
客户端 model=sol
  → 路由到 target A
  → 模型映射得到 gpt-5.6-sol
  → 执行字段删除 / 注入
  → 从最终 body 读取 model
  → 匹配 A 的价格规则并冻结快照
  → 发送上游请求
```

若注入把模型改为其他名称，使用注入后的名称；若最终没有有效 model，记录 `missing_model`，不能回退到被删除的客户端模型。响应的 `model` 只作为诊断信息，不覆盖计价模型，避免上游返回版本名或别名导致价格改变。

### 4.3 快照边界

在读取最终请求体、准备发往上游时，将所选 target、计价模型和规则复制进本次请求上下文。后续 received/pending/finished 更新都携带同一快照；写入队列消费时不重新读取配置。没有匹配规则也冻结这一事实。

当前单 target 场景在读完 body 前就写入 received 事件，该阶段暂时只有 pending 状态；完成解析后补齐快照。在请求运行期间修改、删除规则或删除 target，不改变本次及既有记录价格。

## 5. token 标准化与计算规则

### 5.1 统一四个互斥计费桶

| 字段 | 含义 |
| --- | --- |
| `input_uncached_tokens` | 普通输入，不包含缓存读取和缓存写入 |
| `output_tokens` | 输出 token，包含协议已计入其中的推理 token |
| `cache_read_tokens` | 缓存命中读取 |
| `cache_write_tokens` | 新建缓存写入 |

请求费用：

```text
费用（元）=
  (普通输入 × 输入单价
   + 输出 × 输出单价
   + 缓存读取 × 缓存读取单价
   + 缓存写入 × 缓存写入单价) / 1,000,000
```

不能直接拿现有 `request_token_count` 乘输入价再加缓存费用；这会重复计算缓存部分。现有总输入展示改为从标准化结果派生，在数据完整时等于普通输入 + 缓存读取 + 缓存写入。

### 5.2 按协议解释 usage

| 协议 | 普通输入 | 输出 | 缓存读取 | 缓存写入 |
| --- | --- | --- | --- | --- |
| OpenAI Responses | `input_tokens - input_tokens_details.cached_tokens` | `output_tokens` | `input_tokens_details.cached_tokens` | 标准协议没有独立字段，计 0 |
| OpenAI Chat Completions | `prompt_tokens - prompt_tokens_details.cached_tokens` | `completion_tokens` | `prompt_tokens_details.cached_tokens` | 标准协议没有独立字段，计 0 |
| OpenAI legacy Completions | `prompt_tokens`，若支持上述 cached 明细则扣除 | `completion_tokens` | 已知 cached 明细，否则 0 | 0 |
| Anthropic Messages | `input_tokens`，本身不含两类缓存 | `output_tokens` | `cache_read_input_tokens` | `cache_creation_input_tokens` |

规则约束：

- 协议规定为可选的缓存字段缺失时按 0；必需的输入或输出缺失则不能完整计价。只有 `total_tokens` 不足以拆分费用。
- 缺失与非法值分开处理：负值、小数、非安全整数、字符串 token 值均标为异常；OpenAI cached 大于总输入也标为异常，不能用 `max(0, …)` 隐藏问题。
- 推理 token 若已包含在输出内，不再重复相加；音频等 token 首版沿用所属输入/输出桶单价，不提供独立价格。
- Anthropic 同时包含总缓存写入与 TTL 子项时只用总值；若只有明确支持的 TTL 子项则相加一次，统一用缓存写入价。总值与子项矛盾时标记异常。
- OpenAI 兼容服务如果混入 Anthropic 缓存字段，不猜测输入是否已包含缓存。出现冲突语义时返回 `unsupported_usage`，以后增加有明确测试样本的适配器。
- 未知 endpoint/usage 结构显示未计价，不根据字段名称任意拼凑协议。
- 每个请求的 usage 是该次请求实际消耗，即使输入包含之前的对话也按上游本次值计费；不能在 task 内按上下文内容去重。

### 5.3 SSE、失败和中断

Responses 读取终态事件（包括携带完整 usage 的 incomplete 事件）；Chat 读取最终 usage chunk；Messages 合并 message_start 输入/缓存信息与后续 message_delta 的累计输出，并验证终态。重复累计值采用覆盖，不能逐事件累加。

新增轻量 `UsageAccumulator`，在响应转发时观察 SSE，独立于用于展示内容的摘要上限。它只保留模型、usage、终态标记，不保存文本和工具参数；设置有限的单事件缓冲，例如 1 MiB，超大事件丢弃并恢复到下一事件边界，标记采集不完整，不无限增长内存。普通 JSON 响应从已解析正文提取，超过现有正文上限无法解析时显示缺少用量。

计费观察器不会修改请求或响应，也不为索取 usage 自动注入 `stream_options`。Chat 流未返回 usage 时，详情提示上游未返回用量，可由调用方配置其支持的 usage 选项。

- 正在执行：pending，不用中间累计输出展示一个看似最终的费用。
- HTTP 错误或业务 incomplete，但有完整可信 usage：照常计费，HTTP 状态与计价状态独立。
- 客户端断开，但终态 usage 已完整捕获：可以计费；只收到部分 usage 则 `incomplete_usage`。
- 未收到 usage 的超时、失败、中断：未计价，不自动推断免费。
- 显式四桶全为零、或匹配到四项零单价，且 usage 完整：金额可为零。
- 首版不计算单条请求的部分小计；task 的“已知费用”仅包含完整计价请求。
- 未启用流量日志的 target 不产生历史费用；应用被强制终止留下的 pending 记录不能推算最终费用，UI 应结合活动请求状态标为中断/未完成。

### 5.4 金额精度

配置单价与倍率使用十进制字符串，最多 6 位小数；乘后的快照单价最多 12 位小数。计算使用 `BigInt`，不使用 JavaScript 浮点乘法或 SQLite `REAL` 累加金额。

推荐将单次总费用保存为整数纳元：`1 元 = 10^9 纳元`。配置价格和倍率分别转为百万分之一元的整数并相乘，得到万亿分之一元的实际单价 `P`；四项乘积先相加得到 `S = Σ(token × P)`，最后 `cost_nano_cny = (S + 500,000,000) / 1,000,000,000`（非负整数除法，四舍五入）。每请求只舍入一次，误差不超过 0.5 纳元。

SQLite 使用 64 位 INTEGER，金额相关语句开启安全整数读取，序列化前转为十进制字符串。写入前校验 64 位范围，异常记录 `amount_overflow`，不能丢失精度或阻断代理转发。任务合计同样检查范围；极端聚合溢出时采用 BigInt 批量读取金额累加的受控回退。

分项在内部保留原始整数乘积（相当于最多 12 位小数），请求和 task 详情均按第 3.4 节格式化为最多 4 位小数；总额以单次存储金额为准，不将已格式化分项再次相加。task 四类分项先汇总原始乘积再格式化，而 task 总额累加各请求存储的纳元金额；两者可能有纳元级舍入尾差，不把尾差任意分配给某一 token 类别。

## 6. 配置、持久化与 API

### 6.1 配置结构

在 `TargetConfig` 增加 `model_prices` 数组，示例为 target 配置片段：

```json
{
  "id": "target-a",
  "model_prices": [
    {
      "model_pattern": "gpt-5.6-sol",
      "price_multiplier": "1.2",
      "input_per_million": "5",
      "output_per_million": "30",
      "cache_read_per_million": "0.5",
      "cache_write_per_million": "6.25"
    }
  ]
}
```

数组顺序就是通配优先级，不额外引入 priority 字段或规则 ID。币种固定 CNY，不在每条配置中重复填写。缺少新字段的现有配置正规化为 `[]`；非法新价格必须报错，不能被 normalizer 吞掉或转成零。

沿用现有 `/api/pairs` 读写和配置应用事务：新增配置字段必须穿透默认值、schema、normalizer、运行时 target 构建和 UI 序列化。保存失败继续使用原配置。无需新增独立价格 CRUD API。

### 6.2 数据库设计

基于当前 schema v7 增加下一版本迁移（当前预计 v8，实现时确认版本）。在 `records` 增加：

| 字段 | SQLite 类型 | 用途 |
| --- | --- | --- |
| `pricing_status` | TEXT NOT NULL DEFAULT 'unpriced' | `pending` / `priced` / `unpriced` |
| `pricing_reason` | TEXT NULL | 未计价原因；旧记录默认为 `legacy_record` |
| `billing_model` | TEXT NULL | 实际发出模型名 |
| `pricing_snapshot_json` | TEXT NULL | 命中 pattern、四项乘后实际单价、CNY、计价时间、算法版本 |
| `billing_usage_json` | TEXT NULL | 四桶 token、协议来源、完整性及诊断信息 |
| `cost_nano_cny` | INTEGER NULL | 只有 priced 可非空，零元是有效值 |

已有 `target_id`、`target_name`、`target_url`、`proxy_id` 继续用于追溯；快照不包含 API Key。详情快照和 usage 不参与列表 JSON 解析，列表只取状态和金额。

`pricing_reason` 首批值：`legacy_record`、`no_matching_price`、`missing_model`、`missing_usage`、`incomplete_usage`、`invalid_usage`、`unsupported_usage`、`amount_overflow`。同时存在多个问题时详情附带诊断数组，列表采用固定顺序：模型 → 价格 → usage → 金额，避免文案随机改变。

### 6.3 task 合计策略

首版不在 `tasks` 冗余存储总费用：先按现有搜索、排序和分页取得 task IDs，再用这些 ID 对 records 批量 `GROUP BY task_id` 聚合金额和状态数量，使用现有 task_id 索引。仅扫描可见任务的摘要列，不扫描正文，也不为每个 task 单独发起查询。

聚合不携带搜索关键词；搜索只决定哪些 task 和请求可见。没有 priced 请求时返回 null，不能使用 `COALESCE(SUM(...), 0)` 混淆未知与免费。补全统计满足 `priced + unpriced + pending = 实际记录总数`。

这样同一 record 多次 upsert 不会重复累加；任务重新归组、记录删除与日志清理后总额自然反映当前 records。task 页面和对应费用聚合在同一数据库读事务中取得，多日志目录在每个目录中完成相同操作后沿用现有合并逻辑。历史页面只合计仍保留的日志，清理后的金额不代表终身累计费用。

若大任务查询性能不达标，再考虑持久化聚合；不能直接采用“每写一次就增加费用”，那会对 received/pending/finished 重复记账。

task 费用明细按需查询：读取整个 task 的 `billing_model`、状态、金额、usage 与价格快照，在服务端以 BigInt 汇总四类乘积与分组小计，不读取请求/响应正文。使用迭代或分批读取控制内存；分组很多时按服务端聚合结果分页，顶层总额与四类汇总始终覆盖整个 task。转发地址复用现有 task 摘要，不增加地址去重或集合查询。

### 6.4 API 合同

金额对外使用元为单位的十进制字符串，禁止先转成 JS Number。以下为新增片段，不替代接口其他字段。

请求摘要（组内分页与搜索 preview 使用相同结构）：

```json
{
  "cost": {
    "currency": "CNY",
    "amount": "0.041125000",
    "status": "priced",
    "reason": null
  }
}
```

task 摘要：

```json
{
  "cost": {
    "currency": "CNY",
    "known_amount": "0.042750000",
    "priced_request_count": 3,
    "unpriced_request_count": 1,
    "pending_request_count": 0
  }
}
```

请求未计价或 pending 时 `amount=null`；task 无 priced 请求时 `known_amount=null`。详情 `/api/logs/:id` 在顶层增加 `pricing`，包含相同 cost、billing_model、snapshot、usage 和 breakdown，避免把大量结构塞进普通响应头显示区。

新增 `GET /api/log-groups/:id/pricing?limit=50&offset=0`，为 task 费用面板返回 `id`、`target`（该 task 的转发地址）、`cost`、四类 `breakdown`（已计价 token 数及分项金额）、`unpriced_reasons`（原因及数量）、`groups`（模型/单价/算法版本组合及其请求数、四类明细和小计）及分组分页信息。接口不接受搜索词，聚合和分组分页在同一读快照中完成，任务不存在返回 404。请求详情、task 明细及导出使用同一分项计算函数。

一级摘要沿用现有 `target` 字段，不增加地址数量、地址集合或单地址替代字段。不同地址新开 task 的现有行为保持不变，各 task 独立汇总费用。

需要同步更新 `/api/logs`、`/api/log-groups/:id/logs`、`/api/logs/:id`、新增 task 费用明细接口和配置 API 的响应 schema，否则 Fastify 序列化可能丢掉新字段。导出格式保留费用、usage 和价格快照，脱离当前配置仍可解释历史金额。

前端 `logGroupSummarySignature()` 纳入金额、各状态计数和地址摘要；pending 请求详情轮询结束时同步请求费用并刷新分组摘要。已打开的 task 费用面板随现有自动刷新周期重新获取，避免金额不变但归组或明细变化时遗漏更新；切换 task 时丢弃过期响应。所有列表入口、搜索预览和加载更多复用同一个费用渲染函数，避免仅普通列表显示金额。

## 7. 历史数据与范围取舍

迁移只增加字段与明确的未计价标记，不读取全部历史正文、不按现在价格批量重算。原因是旧记录没有当时价格快照，只有输入/输出汇总时也可能缺乏可靠缓存拆分。

用户后续若需要补算，可另行设计“使用当前价格估算所选旧记录”：先预览覆盖范围，再显式执行；记录估算时间和价格来源，保留未计价原因，不能覆盖已有请求时价格。这项操作不属于首版。

价格由四个固定桶表达，因此供应商针对长上下文、缓存 TTL 或音频的特殊计费只能由用户自行选择代表性单价。页面不宣称金额等于实际账单。

### 8.2 必须覆盖的验收场景

| 场景 | 预期结果 |
| --- | --- |
| 用户示例单价，输入 1,500 / 输出 1,000 / 读 1,000 / 写 500 | 内部精确得到 0.041125 元，UI 显示 ¥0.0411，总输入 3,000 |

| 长 URL、长模型、窄窗口 | 一级固定三行且各行不换行，第一行仅日期时间，第二行模型/请求数/费用，第三行地址；超宽内容允许裁切 |
| task 未展开时点击费用文字（含未计价/计算中） | 直接打开 task 面板，不增加独立明细按钮，不展开/折叠请求列表，不触发选择框 |
| 二级列表增加费用 | 保留标签在上、数字在下的现有结构，只追加费用指标列；消息/请求/响应及时间状态布局不变，各行不自动换行 |
| 同一 task 中同模型多次改价 | 四类汇总正确，按实际模型及价格快照分组，不套用当前价格 |
| 请求切换到不同转发地址 | 沿用现有行为新开 task，每个 task 只显示自身地址并独立汇总费用 |
| task 明细处于搜索、请求分页、分组分页、未计价混合状态 | 总额与四类汇总始终覆盖全部已计价请求，未知原因数量完整 |
| 同模型不同 target、同 URL 不同 target ID | 各用自身价格 |
| 精确项与 `*` 重叠、多条通配规则重排 | 精确优先，其余首条命中；测试框与后端一致 |
| 模型别名映射、模型字段注入/删除 | 使用最终实际发出模型；删除后明确未计价 |
| 请求进行中修改或删除价格 | 本次仍用原快照，下次使用新配置 |
| OpenAI cached 已计入 input/prompt | 普通输入扣除缓存，绝不重复收费 |
| Messages input 不含两类缓存 | 四项分别计费，TTL 子项不重复相加 |
| SSE 分包、重复累计 usage、终态 usage、超过摘要上限 | 标准化金额与相同 JSON 响应一致；不完整采集明确标记 |
| 缺 usage、异常 usage、非 2xx 有完整 usage、中断 | 按第 5 节规则区分状态，不能一律计零 |
| 单价 0、小额费用、金额大于 JS 安全整数 | 零与未知不同，小额不显示假零，大额无精度损失 |
| 一个 record 的多次写入、重新归组和删除 | 总额不重复，旧组和新组均正确 |
| 200 条以上请求、搜索仅命中一条、多个日志目录 | 一级始终是 task 全额，分页与 preview 金额一致 |
| 升级旧数据库、删除 target、重新打开应用 | 旧数据标未计价；已有快照可独立解释 |
| 配置新增字段/API 响应/日志导出 | 字段往返无丢失，错误价格保存失败并保留原运行配置 |

性能验证重点是万条记录搜索、单 task 数千请求、多个日志目录，以及长 SSE 的缓冲上限；比较现有基线，确认新增聚合不读取正文、不重复 FTS 查询、不引入 N+1。

## 9. 评审重点

建议优先审阅四个产品取舍：

1. 按实际转发模型定价，而不是客户端别名或响应模型名。
2. 精确优先，通配规则按界面顺序命中。
3. 改价只影响新请求，旧日志首版不自动补算。
4. task 列表只显示已知金额合计，保持一级列表紧凑；已知/未计价/进行中的数量与原因在费用明细面板展示。

以上均为推荐方案，可以在实现前调整。本文不执行应用功能修改或提交。
