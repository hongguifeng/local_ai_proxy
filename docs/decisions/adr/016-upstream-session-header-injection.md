# ADR-016：缺失的上游会话头由代理按需补齐，且不覆盖客户端已有的值

## 背景

有的上游把会话标识当硬性合同。OpenCode Go 现在对没有会话头的请求直接返回 400 `MissingSessionID`，而这个头的作用只是把同一段对话的路由和 prompt cache 粘在一起。客户端不一定每条请求路径都发它：pi 1.5.0 打 OpenCode Go 的实测历史里，主对话链路带 `session_id` 且全部成功，上下文压缩走另一条自己拼 headers 的路径，一条会话头都没带，全部 400。

代理已经在转发前完整收集了请求体，压缩请求体本身还带着整段会话。因此“补一个稳定 id”在代理这一层是可行的，而且不必等客户端修。

## 决定

1. 目标配置新增 `session_header`（Header 名，默认空即关闭）。关闭时转发集合与今天完全一致。
2. 启用后，只有在转发集合里**没有**这个头时才补：客户端或 `target_headers` 已经给了值就一律不动。
3. 值的来源有顺序：客户端已经发出的会话头（`session_id`、`x-session-affinity`、`x-claude-code-session-id`）优先复制；都没有才按请求内容派生 `proxy-<hash>`。
4. 派生是纯函数，输入是 `{kind, model, 去掉 first_user 的边界指纹, 首条用户文本前 4096 个字符}`，因此同一会话的连续请求和同一会话的多次压缩请求取到同一个值，重启后也不变，不需要落盘状态。
5. 补头的事实写进记录的 `added_upstream_headers`，只记名字，不记值。

## 备选方案与为什么不选

- **什么都不做，让用户改客户端**：pi 的压缩路径就是漏头的那一侧，且用户手上是扩展随包的固定版本。代理是自己能改的那一层，把兼容放在这里最省事。
- **按域名自动识别 OpenCode**：自动魔法会让“为什么这个目标多了个头”无法解释，也会在别人自建的兼容网关上误补。启用必须是显式的用户决定。
- **固定值（等价于 `target_headers` 写一行）**：能消掉 400，但所有会话共用一个桶，路由亲和与 prompt cache 都失去意义；而且 `target_headers` 会覆盖客户端自己的头，把客户端已经正确的分桶改坏。
- **覆盖成代理自己算的值**：能保证“所有请求同一个 id”，但会替换客户端已经发出的会话 id，把今天正常工作的路由改掉。收益是压缩请求和主对话同桶，代价是主对话全部重分桶，不划算。
- **把压缩请求模糊匹配回主对话的会话 id**：需要在几百 KB 的请求体上跨记录匹配，误判会把不相干的会话粘在一起。一次冷启动比粘错会话便宜，因此不做。

## 后果

- 该字段默认关闭，老配置的转发行为不变；只有显式写了头名的目标才会多一个头。
- 压缩请求的分桶与主对话不同（客户端那一侧用的是它自己的 `session_id`，压缩请求没有任何客户端会话证据）。这个代价是一次冷启动级别的缓存未命中，写进了设计文档第 7 节，不是缺陷。
- 派生 id 在会话被压缩替换历史后会变化，这是分桶的一次性边界：换了首条用户文本就是换了会话证据。
- `added_upstream_headers` 从此有真实产出方：以前它只出现在日志和存储层的合同里。
- 上游对会话头的格式没有公开约束，代理发的是 30 字符的 `proxy-<24 位十六进制>`；如果某个上游要求特定格式，需要再开一个字段而不是在这里猜。

## 证明方法

- `test-node/proxy/session-header.test.ts`：关闭时零改动、已有同名头零改动、三个来源头的顺序、同会话相同 / 跨会话不同、非 JSON 退回路径哈希。
- `test-node/proxy/proxy-listener.test.ts`：真实监听器里上游收到的头集合，以及记录里 `added_upstream_headers` 只有名字。
- `test-node/proxy/load-balancer-pipeline.test.ts` 的 SH-09：第一次尝试被重置后，第二个节点收到同一个派生值。
- `test-node/config/config-schema.test.ts`：非法头名按 `invalid_config` 拒绝。
- `test-node/ui/admin-ui-proxy.test.ts`：输入框存在、保存后进入配置、留空即关闭。
