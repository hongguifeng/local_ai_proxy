# ADR-013：负载均衡采用粘性任务路由 + 最少在途选择

## 背景

同一模型有两个等价上游（两张显卡，`9393` / `9394`）。需要在代理侧把新请求分派到负载较轻的节点，同时保证同一 task 的请求固定在同一节点：vLLM 的 KV/前缀缓存只存在于处理过该上下文的实例上，改道意味着整段上下文重新 prefill（长上下文可达数十秒），并可能在目标节点触发缓存淘汰，连带毁掉其他 task 的缓存。

现有选择规则只有「按 `model_mappings` 命中」和「默认地址」两种，无法表达「同一模型的多个等价副本」。

## 选项

1. **纯轮询（用户直觉方案）**：记住上一次落点，新 task 交替发往另一节点。
   - 优点：实现极简、无外部依赖、不需要指标。
   - 缺点：忽略真实并发（刚发出的 prefill 仍只是「上一次落点」）、长解码请求长时间占位、异构显卡被强制 50/50、粘性造成的 KV 常驻完全不可见、节点故障时会继续轮流打到死端口。
2. **纯最少在途（代理侧计数）**：选未完成请求最少的节点。
   - 优点：无外部依赖、确定性好、对新突发自适应。
   - 缺点：看不到绕过代理直接打在引擎上的负载；「一个 200k prompt 的 prefill」与「一个 50 token 的请求」同权；不知道 KV 显存压力。
3. **代理侧最少在途 + 上游 `/metrics`（vLLM/SGLang/llama.cpp）真实排队 + KV 分档**：轮询降级为平级判据。
   - 优点：同时覆盖「我们看到的」与「引擎真实承受的」负载；KV 余量可保护其他 task 的常驻缓存；无指标时可退化为选项 2。
   - 缺点：需要后台采样器与指标解析；指标名会漂移；每个节点多一份周期请求。
4. **在节点之间迁移/共享 KV 缓存**（KV transfer、LMCache 等）。
   - 优点：理论上可以自由重平衡。
   - 缺点：需要引擎侧支持与额外部署，超出代理职责；本项目不引入。

## 决策

采用**选项 3**，并明确三层语义：

### 1. 粘性优先于负载

路由先按「task 亲和证据」查绑定，命中即用绑定节点，**不比较负载**。负载只在「新建绑定」时参与。

- 证据分两类：精确键（`previous_response_id`、`conversation`/`thread`/`session` id、`x-claude-code-session-id`、`prompt_cache_key`）与前缀证据（kind + endpoint + model + 边界指纹 + 用户消息哈希前缀 + 继续证据）。
- 判据与日志 `TaskMatcher`（策略版本 6）同源：抽取到共享纯函数模块，matcher 与路由共用，禁止两套语义。
- 一致性方向固定为「路由判定 ⊇ matcher 判定」。路由更松只会让流量略偏；路由更严会出现「同一 task 分别落在两个 target」，正是本 ADR 要避免的现象。
- 绑定是**内存**结构（精确键索引 + 前缀桶，TTL 24h，容量 LRU）。选择路径全同步、无 I/O，因此同一 task 的并发请求与突发新 task 都不会重复建绑或扎堆（选路时立即预留 `inFlight`）。

### 2. 新 task 用「分档 + 最少在途 + LRU」排序

```text
tier   = kvUsage >= 0.9 ? 1 : 0                                  # KV 余量优先
load   = max(inFlight, running + waiting)                        # running/waiting 来自采样
sort by (tier, load, lastDispatchedAt, kvUsage, configIndex)
```

- `max` 而不是相加：`running` 已包含代理自己的在途，相加会重复计数；采样有延迟，取最大值可覆盖刚发出的请求。
- `lastDispatchedAt` 升序即用户直觉中的轮询，但只在前面几项相同时生效，因此「两台都空闲」时表现为交替。
- 采样过期（`max(3×间隔, 15s)`）或缺失时完全退回 `inFlight`，不因为「不知道」惩罚节点。
- 提供 `strategy: "round_robin"` 作为显式选项（纯交替，仍遵守粘性），用于没有 `/metrics` 的引擎或需要严格交替的场景。

### 3. 组内模型名由成员自己的 `model_id` 决定，节点模型映射失效

组成员 target 的 `model_mappings` 不参与选择，也不改写模型名。上游模型名取被选成员的 `model_id`：为空时透传请求模型，非空时用它改写（LB-19）。亲和键记的是客户端请求的模型名，不是改写后的名字，所以改映射不会把已绑定的任务从原节点上挪走。

成员填不同模型名时，安全切换会连带换掉上游模型名——这是设计后果，不是缺陷：粘性保证同一个任务在同一张卡上模型名始终一致，只有节点真的换了才会变，并且记进 `model_route.upstream_model`。

其余节点级配置（URL、Key、Headers、strip/inject、日志目录、脱敏、价格）继续按最终落点生效。

## 后果

- 保存配置不会打断粘性：`LoadBalancer` 挂在 pair 运行时条目上，`reloadPair` 只调 `reconfigure()` 原地更新（ADR-011）。只有被删/被禁用的节点会丢绑定。
- 进程重启会丢失绑定（v1 不持久化）；活跃会话的下一个请求按负载重新选择，可能换节点并重新 prefill。v2 的推荐做法是首个未命中请求回查流量库中匹配 task 的最后一条 record 的 `target_id`。
- 每个被引用节点每 5 秒一次 `/metrics`（仅采样成功才参与打分）。采样失败只影响打分精度，不影响转发；失败/恢复各记一条日志。
- 连接期失败（未向客户端写出字节）触发一次失败切换，并把该 task **重新绑定**到新节点（上下文已在新节点重算）。上游返回 4xx/5xx 不切换；已开始写响应后绝不切换。
- 记录层不新增列：决策细节写入既有 `request.model_route` JSON（`route_mode` / `load_balance.{decision,load,kv_usage,failover_from}`），并已通过请求元信息面板可见。
- 代理重启、绑定淘汰、节点移除、失败切换是「同一 task 可能换节点」的全部已知原因，必须在用户文档中如实列出。
- 已知限制：prompt 长度不参与打分；异构节点无权重；模型名必须两侧一致；同构前缀的独立会话可能共享一次绑定（方向安全）。

## 实现状态

三项决策都已落地，代码位置见[模块设计 §7.4](../../history/python-baseline/module-design.md)。
真机验收（设计文档 §13.4）给本 ADR 补了两条约束：

1. 上游不保存 response 时，`previous_response_id` 链无法作为亲和证据：
   代理只能从非流式响应体里读到 response id，流式 SSE 摘要里没有 id。
   这类部署的粘性依赖会话头或 `prompt_cache_key`。
2. “组内价格必须一致”在生产配置上尚未成立：两张卡的 `cache_write_per_million`
   一个是 `0`、一个是 `1.25`，校验会拒组。要开启负载均衡必须先对齐价格规则。
