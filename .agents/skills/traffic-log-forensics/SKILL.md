# Reading traffic history without the native module

These traps were learned in this repository and moved here verbatim from `AGENTS.md`;
nothing was paraphrased.

- Traffic-log forensics without touching native modules: open `logs/traffic.db` with Python's stdlib `sqlite3` — after `npm run rebuild:electron`, `better-sqlite3` carries the Electron ABI and a plain `node -e` require fails with `NODE_MODULE_VERSION`. Streamed bodies are stored in `body_chunks` (`record_body_chunks.chunk_hash` → `body_chunks.data`); `codec=deflate-raw-1` needs `zlib.decompress(data, -15)`, not the zlib wrapper. Judge token/speed claims against the upstream engine's `/metrics` counters (`prompt_tokens_by_source_total{source="local_compute"}` ÷ `request_prefill_time_seconds_sum` gives real prefill throughput) instead of trusting history chips: the Prefill chip divides by `first_token_ms`, which also covers proxy body parsing and upstream tokenization, so it is only an approximation. Triage an all-`unpriced` task the same way: pull the response `usage` object out of `body_chunks` and read it against `pricing_reason` — a whole task stuck on `invalid_usage` on an OpenAI-compatible upstream is normally an explicitly `null` optional field (vLLM sends `prompt_tokens_details: null` when cache accounting is off), not malformed token counts. Conversely, a task that shows only end-to-end speed is expected, not a bug: `first_token_ms` and `decode_window_ms` are sampled only for SSE responses, so buffered non-stream requests have neither and the UI must fall back to end-to-end. The `request_body_json` / `response_body_json` columns are NULL for every updated record (the upsert's `ON CONFLICT DO UPDATE` nulls them once the text has been chunked, and `getRecord` re-reads them through `loadRecordBody`), so `json_extract(request_body_json, ...)` silently returns nothing - rebuild a body by concatenating `record_body_chunks` in `chunk_index` order, or read what you need from `request_headers_json`, which _is_ stored inline and cheap. "Which upstream served this?" never needs a body: `records.target_id` / `target_url` say it directly, and `context_links` (`prompt_cache:<key>` → task) plus `tasks.target` already exist for durable routing-affinity experiments - `tasks.target` is `scheme://host:port` + that record's request path, so match it against a node by origin+basePath rather than verbatim. A bounded scan of the 14 GB production DB is affordable (`SELECT ... FROM (SELECT col FROM records ORDER BY timestamp DESC LIMIT 3000)` → 20 ms for a header-only column, ~450 ms when it parses 3000 headers), so distribution questions about sessions and upstreams are answerable without booting the app.
