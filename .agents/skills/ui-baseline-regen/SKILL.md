# Admin UI visual baselines: regenerate, sync, compare

These traps were learned in this repository and moved here verbatim from `AGENTS.md`;
nothing was paraphrased.

The always-on rule lives in `AGENTS.md`: regenerate baselines before committing and
update the README images plus the hashes in the baseline doc. Everything below is
how to do that without fooling yourself.

- The usage-statistics API contract is unit-sensitive: `overview` totals and byTarget/byModel `cost` are yuan strings, while trend `points[].cost` is a nano-CNY integer the UI divides by 1e9; derived values like averages must be computed with exact integer division on the nano values and only then converted to a decimal string (a naive float average of yuan values can come out as 0.014249999999999998 and format as 0.0142, one last-digit off versus the exact integer mean 0.0143); new baseline rows in the doc need a real SHA-256 hash (the regen script's row regex only matches a full 64-char `[0-9a-f]{64}` cell, so it rejects `PENDING` placeholders or truncated hashes like `f81eaa20a8d1…` — a row with a shortened hash makes the full-regen doc-sync step fail, so keep/restore the complete hash; for a panel-only change regenerating just the two task-detail baselines is enough, the other six stay byte-identical). To add a _new_ baseline without disturbing the existing ones, capture only it (`REGEN_BASELINES=1 npx vitest run test-node/ui/admin-ui-visual.test.ts -t "<new test>"` — `screenshotDifference` writes the file and returns 0) and hand-fill its doc row; a full `npm run regen:ui-baselines` re-captures every page and can drift the stats page. The same selective capture also works for _updating_ an existing baseline whose content changed: `REGEN_BASELINES=1 npx vitest run test-node/ui/admin-ui-visual.test.ts -t "load balancing baseline"` re-captured only the two LB pages and the other eight stayed byte-identical. Baseline assertions compare a differing-pixel ratio with `toBeLessThan(0.12)`, not a zero pixel count, so a localized change such as swapping two adjacent header controls (measured 2952 of 1508040 pixels, 0.2 %) passes while the committed PNG still shows the old arrangement - any markup-order change needs a re-capture plus a pixel diff against HEAD to prove the delta is real.
- The task-detail (pricing) baseline uses an adaptive viewport: after the panel opens, the test resizes to the panel's scrollHeight + 52 (like the statistics baseline), because the panel is inset:0 with its own scroll — a fixed-height viewport silently hides the bottom of the panel in the PNG. Adding a panel block therefore changes the baseline image height; update the doc row. If a newly added panel section is missing from a regenerated baseline, compare the element's bounding rect against the panel's `clientHeight` (and `scrollHeight`) before assuming the screenshot is wrong — the panel simply isn't scrolled in the capture.
- Regenerated UI-baseline PNGs can change bytes/hashes (encoder metadata non-determinism) while remaining pixel-identical; before treating a baseline change as a visual regression, diff committed vs regenerated images pixel-wise (e.g. `pixelmatch` + `pngjs`, threshold 0.1, expect 0 differing pixels). If the test baseline was committed from another machine, local regen can shift hashes for every page at once — compare against a stash of the pre-change source to separate your effect from environment drift. Environment drift can also shift the _document height_ by a few px (fractional-pixel rounding) with identical visible content; `screenshotDifference` therefore tolerates a height delta ≤ 4 px as long as the taller side's extra rows carry no content — "blank" there means channels ≥ 200, not > 230, because the pane splitter border (213,221,231, six pixels a row) sits in the bottom rows of the adaptive task-detail capture and a one-pixel viewport drift on `windows-latest` failed the stricter rule. Do not reintroduce strict size assertions there. The inverse trap: a hash change with a pixel-identical image can also mean the on-disk PNG is a _stale_ regeneration from before the code change took effect (non-`REGEN_BASELINES` `screenshotDifference` only reads and never writes, so a green test proves nothing about the baseline file). When a baseline appears unresponsive to a UI change, verify in order: (1) the served static assets actually contain the new string — the vitest harness serves `src/admin/static` but the built app serves the `dist-node` copies, so check both; (2) the new DOM content actually renders — a throwaway `page.evaluate` dump of the changed text/nodes is the fastest conclusive check, faster than pixel archaeology; (3) then pixel-diff the on-disk file against HEAD. A control relocation between rows can pass the assertion anyway - moving the target card's three action buttons out of the head, together with a card fill change, measured 8.9-10.2 % differing pixels against the committed PNG, still under the 0.12 limit - so re-capture after any such move instead of trusting a green baseline test.
- `npm run regen:ui-baselines` can drift `ui_stats_*` for a pre-existing reason unrelated to your change: the trend grouping select in `app.js` is read via `$("statsBreakdown")?.value || "model"` before the select may exist, so the stats page can be captured with the "model" breakdown instead of the default "total" (a different legend/bar colors and ~2px document height). If the stats page is the only visual change and you did not touch stats code, resolve the conflict by comparing hashes, not by restoring blindly: the committed `ui_stats_*` PNG bytes have at times not matched the committed doc hashes (the two artifacts were captured in different environments), while a local regen converges exactly to the doc hashes — in that case adopt the regenerated stats PNGs (no doc edit needed) and re-diff the PNGs pixel-wise to prove your change left the stats page visually untouched. Restore the committed PNGs only if the regen hash matches neither. Note that restoring the doc via `git checkout` also resets any uncommitted table fixes in it (e.g. a restored/added column) — re-apply those after the restore.
