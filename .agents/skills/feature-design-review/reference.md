# 功能设计参考：从设想到可验证合同

配合 [SKILL.md](./SKILL.md) 使用。正文是可复用方法，例子只展示怎样核对证据；
不要把某个功能的运行代号、请求边界或数据库选择直接套到其它功能。

## 1. 研究步骤与最小产物

| 步骤     | 要解决的问题                                         | 最小产物                               |
| -------- | ---------------------------------------------------- | -------------------------------------- |
| 还原需求 | 用户希望改善什么；任务是否包含多个必须一起研究的问题 | 目标、成功标准、范围与非目标           |
| 建立现状 | 当前代码由哪里读写，何时对外生效                     | 核心调用链、状态所有者与证据表         |
| 验证前提 | 设想需要的信息或能力是否存在                         | 已有、需新增、未知、外部依赖四类清单   |
| 比较选项 | 哪个选择能以合理成本满足需求                         | 推荐、替代、不做的后果                 |
| 固定合同 | 动作对什么生效，冲突、失败和取消如何处理             | 数据归属、状态机、API/UI 动作表        |
| 设计验证 | 什么结果能推翻推荐，如何判断用户收益                 | 反例、逻辑测试、性能实验及阶段出口     |
| 收敛文档 | 原稿、修订与现行行为如何区分                         | 唯一结论入口、变更记录、关联需求的验收 |

不要为收集更多文件而无限扩展。优先核对会改变推荐结论的事实；可暂缓的未知放到问题表，
关键未知说明为何阻塞及下一步证据。代码里的当前实现是事实来源，不等于它已经是最佳方案。

## 2. 证据表和数据权威表

建议记录：

| 结论         | 类别       | 证据位置或实验                       | 适用范围 / 未覆盖项 | 对方案的影响       |
| ------------ | ---------- | ------------------------------------ | ------------------- | ------------------ |
| 当前运行行为 | 已核对事实 | 当前提交、文件、符号、必要行号与测试 | 适用配置与路径      | 保留或明确替代     |
| 拟增加的行为 | 设计选择   | 对应需求与取舍                       | 前提及非目标        | 进入合同和验收     |
| 某阈值或收益 | 待验证假设 | 校准或对照实验计划                   | 尚无当前实测        | 不写成默认已证行为 |
| 实验观察     | 本次实测   | 脚本、输入、版本、结果               | 合成或真实环境      | 只支持覆盖的结论   |

对将被读取或修改的每类对象，再回答：

| 项目     | 必须说明                                            |
| -------- | --------------------------------------------------- |
| 身份     | ID 的作用域、是否复用、与其它对象一对一还是多对多   |
| 所有者   | 谁持有生效状态；谁只是缓存、历史或界面投影          |
| 写入口   | 创建、普通更新、失败重试、配置重载、恢复/导入和清理 |
| 读语义   | 当前值、历史值、推导值、聚合值；读取本身有无副作用  |
| 生命周期 | 创建、应用、实际执行、结束、失效与迟到回填          |
| 影响范围 | 一次操作改变哪些对象；用户看到的名称是否足以辨认    |
| 缺失处理 | 未知、零、过期、部分字段缺失分别怎么呈现和决策      |

没有一对一关系时，不要用“选一个代表任务”隐藏其它受影响对象。若关联只是历史推断，
标注范围和置信度，不把它自动升级为写操作的定位依据。

## 3. 如何核对“只有这个方法会写”

从字段和行为找入口，不能只搜一个方法名：

1. 找模型定义、构造/反序列化、直接赋值和全部相关方法。
2. 沿调用者检查普通路径、失败路径与重载路径。
3. 看方法是否同时更改时间、计数、索引、缓存或持久化。
4. 读相关测试；缺少反例时可用小型隔离探针验证关键前提。
5. 将真实写入口列入方案，避免新入口绕过旧合同。

项目例子：

- [load-affinity.ts](../../../src/proxy/load-affinity.ts) 的 `rebind()` 会更新目标与时间；
  `bind()` 的 allowRebind 路径也能修改目标；`lookup()` 会 touch 时间与计数。
  因此“唯一写入口是 rebind”或“requestCount 就是真实轮次”都需要额外核对。
- [proxy-request-pipeline.ts](../../../src/proxy/proxy-request-pipeline.ts) 在响应结束前就会写入
  received/pending 记录；这不代表数据库可以充当可靠实时锁，也不能说在途记录完全不存在。
- [repository.ts](../../../src/persistence/repository.ts) 把 response 与 context 的索引查询分开。
  看起来相似的身份键，不代表可以调用同一个仓储方法。

这些是核对入口的示例。引用时重新检查当前源码，不把本文符号描述当永远不变的实现合同。

## 4. 写操作的竞态与失败矩阵

选实际涉及的行；不适用的项目简要说明，不强制实现每种机制。

| 场景                     | 需要定义的结果                                       |
| ------------------------ | ---------------------------------------------------- |
| 两个页面同时修改         | 同一旧版本提交应冲突还是允许覆盖；API、UI 与测试一致 |
| 同请求网络重放           | 同幂等键同参数的返回；改参数是否冲突；结果保留边界   |
| 旧页面跨重启/重建        | ID 是否复用；是否需要运行代号或不可复用句柄          |
| 检查后配置被修改         | 原地改 URL、模型、目录或转换规则是否仍是同一个目标   |
| 已执行后客户端未收到响应 | 重试怎样辨认已执行，不重复副作用                     |
| 请求仍在飞时修改状态     | 旧请求后续失败、重选、回填与释放依据哪份状态         |
| 清理先于迟到回调         | 回调不能复活已删除对象或误写新对象                   |
| 内存成功、落盘失败       | 哪部分已生效；是否回滚；怎样重试与恢复               |
| 用户动作与自动策略竞争   | 优先权、保护期限、取消及实际生效原因                 |
| 关闭功能或回滚配置       | 停止新动作还是撤销已完成动作；两者代价分别是什么     |

同步检查与赋值只覆盖那一段原子性。画清跨 await 的时间线，才能判断它是否需要锁、版本、
取消标记或其它机制。不要一见“单线程”就断言不存在竞态，也不要默认所有功能都需要新队列。

## 5. 动作表：正文、状态、接口与界面的共同来源

| 动作 | 前置条件与输入             | 状态变化 / 副作用    | 返回与错误         | UI 状态          | 验证编号 |
| ---- | -------------------------- | -------------------- | ------------------ | ---------------- | -------- |
| 提交 | 目标引用、版本、必要参数   | 已接受还是立即执行   | 成功、等待或拒绝   | 禁用/等待/可取消 | 关联需求 |
| 执行 | 复核哪些条件、基于哪份配置 | 修改的唯一对象及范围 | 冲突、失效或已应用 | 何时显示生效     | 关联需求 |
| 重试 | 是否已执行、参数是否相同   | 不重复哪个副作用     | 原结果或冲突       | 重试/刷新        | 关联需求 |
| 取消 | 还能取消到哪个阶段         | 什么保持、什么撤销   | 已执行时如何反馈   | 可取消/已结束    | 关联需求 |

接口样例必须能按表走通。逐条检查：被禁用的按钮是否仍在成功示例中提交；正文的拒绝条件
是否有服务端检查；同一动作是否既要求乐观并发又允许所有旧写入成功。

对管理端变更，按 [admin-api-probing](../admin-api-probing/SKILL.md) 检查实际路由、schema、
服务合同、生产装配、浏览器 API 合同和真实应用测试。路由总数由当前代码和测试推导，
不要把别的方案里写过的数字直接加减后当完成清单。

## 6. 测量前先证明实验对象正确

### 夹具的前置断言

| 要证明什么        | 测量前至少确认                                       |
| ----------------- | ---------------------------------------------------- |
| 满桶 / 容量上限   | 实际独立对象数达到目标；不同输入没有被去重为同一对象 |
| 未命中 / 最坏扫描 | 走到目标分支且扫描达到期望范围，不能只看返回值       |
| 数据库现行性能    | 使用真实迁移与索引，或明确列出与产品 schema 的差异   |
| 并发与重试行为    | 确实跨过设计中的异步边界；不是纯同步循环冒充并发     |
| 缓存冷/热对比     | 记录初始状态、公共前缀、缓存命中口径与其它负载       |
| 生效与审计        | 真实执行有独立证据，不能仅凭日志存在或缺失判断       |

没有对象数断言，“造了很多键”可能只造了一个共享对象；手工写版本号也不会自动创建该版本的
真实表和索引。优先用实际创建路径构建实验对象。

### 数字能证明到哪里

| 数字                     | 能支持                                  | 不能自动支持                   |
| ------------------------ | --------------------------------------- | ------------------------------ |
| 纯函数或内存扫描耗时     | 相同输入与分支下的局部成本              | 整体请求吞吐、真实引擎收益     |
| 合成 SQLite 查询         | 指定 schema、规模和数据分布下的查询形状 | 用户真实大库的响应时间         |
| 单次 TTFT 或缓存比率     | 该请求的观察值                          | 整个任务更快、变化由某动作造成 |
| 在途数或分布更均匀       | 负载分布的一个侧面                      | 用户任务完成时间改善           |
| 一次模型研究耗时 / token | 本题端到端资源与交付差异                | 推理速度、成本或总体能力排名   |
| 句长、标题和强调密度     | 文档结构及潜在阅读负担                  | 实测阅读速度或理解正确率       |

测量记录至少包含：要检验的结论、工作目录、可复跑脚本/命令、输入规模与分布、环境版本、
前置断言、样本与汇总方法、对照条件、结果及有效范围。性能阈值没测过就留作待校准，
逻辑安全规则则应由不变量解释，二者不要混为一谈。

重要证据若需要长期支持设计，随设计保留脚本或足以重建的脚本正文及结果。不能仅引用被删除的
临时脚本路径，也不要为了做指标图侵入用户正在运行的配置或数据库。

## 7. 文档模板与方案变更

使用 [design-doc-readability](../design-doc-readability/SKILL.md) 的结构约束，按变更大小裁剪。
对简单设计可合并相邻小节；对不适用项简写理由，不能编造内容凑表。

```text
标题 / 状态 / 基线 / 权威入口
一句话决策摘要
用户目标、编号需求与明确非目标
现状证据与需改变的合同
推荐与替代方案：为何选择、代价和适用前提
对象身份、状态所有者与接口/UI 动作表
生命周期、竞态、失败、恢复和关闭行为
数值来源、已做实验与未查证事项
实施阶段与出口验证（逐条关联需求）
问题 / 建议 / 替代
可勾选验收清单
```

文档状态区分研究提案、待收敛规格、已采纳设计、已实现行为和历史材料。不要把本轮
“写完文档”勾选成“未来功能验收完成”。

已有方案变更用一张小表记录：原合同、保留/替代/暂缓、理由、受影响需求与文件、验证。
新版本定稿后同步正文、状态机、API 示例、UI 文案和验收；明确旧方案身份与新权威入口。
保留的反对意见若仍影响决策，留在问题表，不散落成两份互相冲突的实施规格。

同题模型比较仅在用户授权时采用。任务说明、基线、权限和预设评价维度保持可比较；
不要把题目拆给不同模型后比较总体能力。保留原稿，在独立评审里列错误，不静默修好原稿再评分。

## 8. 交付自检

- [ ] 需求范围与用户一致，区分共同研究、独立研究、分工和仅评审等不同任务。
- [ ] 关键事实可定位当前代码；“唯一入口”和否定性断言经过完整引用检查。
- [ ] 每种状态的权威、身份作用域和操作实际影响范围明确；未知不冒充零值。
- [ ] 并发、重试、配置变更、重建和清理按适用风险有一致处理。
- [ ] 正文、状态机、API/错误码、UI 与验收能逐条对照，没有互相矛盾。
- [ ] 夹具前提已验证，数字有来源；结论没有越过实验证明范围。
- [ ] 推荐能满足用户成功标准；便利指标、直觉相关性不代替收益证据。
- [ ] 最小交付和扩展有区分；文档状态及唯一权威入口清楚。
- [ ] 已执行验证与实现后计划分开记录，遵守用户实例隔离和项目交付要求。

存在阻塞项时完成可交付的研究，明确阻塞证据与最小下一步；不要用自动审批流程代替判断，
也不要把尚不确定的方案宣告为可直接实现。
