# Portable packaging and smoke launches

These traps were learned in this repository and moved here verbatim from `AGENTS.md`;
nothing was paraphrased.

- The portable exe is an NSIS wrapper around a 7z-compressed `win-unpacked` payload: raw string search in the `.exe` misses code; verify build contents in `release/win-unpacked/resources/app.asar` (or extract the 7z payload with 7-Zip). When an LLM Proxy instance is already running, do not assume it is your own test launch — the exe name and version are unchanged across consecutive same-version builds; check the process creation time and extraction path (portables unpack to a `Temp` dir) before querying or killing it, and only kill processes you started.
- Portable exe build: use `npm run package:electron:portable` to avoid also building the NSIS installer. `electron-builder.env` (auto-loaded by the CLI, listed in .prettierignore) sets `ELECTRON_BUILDER_COMPRESSION_LEVEL=1`; shell environment overrides this value. Level 1 trades a slightly larger exe for faster packaging; measure compilation, native rebuild, and packaging separately before tuning compression. `package:electron:dir` skips exe compression for local debugging. `win.electronLanguages` trims the 46MB locales dir to the wanted `.pak` files, but the matching is exact-per-locale: it must be `en-US`/`zh-CN`-style codes — a prefix like `en` or `zh` deletes ALL 55 locales and breaks the UI.
- Windows login items (auto start): Electron's `setLoginItemSettings` supports a `path` option (Windows) that registers an arbitrary executable under the Run value named `electron.app.<app name>`; the portable NSIS launcher deletes its temp unpack dir on exit, so register the stable `PORTABLE_EXECUTABLE_FILE` it exports (fallback: `PORTABLE_EXECUTABLE_DIR` + `PORTABLE_EXECUTABLE_APP_FILENAME`) instead of the default `process.execPath`. Read-back is path-sensitive: `getLoginItemSettings` must receive the same `path`/`args` used at write time or `openAtLogin` reports false; turning off removes the value by name regardless of `path`. Probe these semantics cheaply with a `.cjs` Electron script via `npx electron` — the harness presets `ELECTRON_RUN_AS_NODE=1` in this shell, which silently degrades the launch to plain Node (clear it from the child env when spawning packaged exes too).
- Packaging content and smoke entry point: `npx asar list release/win-unpacked/resources/app.asar` is the fastest way to confirm what ships (electron-builder `files` now excludes `dist-node/test-node/**` — ~285 fewer entries, a ~2 MB smaller asar); to read one entry back, `@electron/asar` `extractFile(archive, filename)` needs both arguments and wants the backslash-separated path **without** the leading `\` that `asar list` / `listPackage` print (`dist-node\src\admin\static\app.js`): the listed form raises `"…" was not found in this archive`, forward-slash paths raise the same, and a one-argument call reads the string as the archive path and dies inside `readArchiveHeaderSync`; bash eats escaped backslashes in `node -e` / heredoc source, so build that path in a script file by joining segments with `String.fromCharCode(92)`. `npm run smoke:artifact` inherits this shell's `ELECTRON_RUN_AS_NODE=1` and never clears it, so a packaged `LLM Proxy.exe` degrades to plain Node and dies at once (exit 0 for `release/win-unpacked`, exit 9 `bad option` when the portable stub forwards the flags) with no output at all — delete the variable from the child env before reading anything into that result. The portable stub unpacks into a Temp dir named for the app version, so a smoke launch while the user's same-version portable instance is running shares that dir and the app never binds its admin port; `did not become healthy` there is not a packaging regression. Verify the payload without that collision by running `release/win-unpacked/LLM Proxy.exe --no-browser --port <free>` with `ELECTRON_RUN_AS_NODE` deleted and polling `/api/health`. App flags such as `--port` only reach the app when the exe runs as Electron: with `ELECTRON_RUN_AS_NODE=1` Node parses the argv instead and dies with `bad option: --port` (exit 9), which is the death previously attributed to `release/win-unpacked/LLM Proxy.exe` — with the variable cleared that unpacked exe accepts `--no-browser --port <free>` and serves `/api/health` in about a second. `npm run smoke:artifact` must still target the portable artifact because the stub plus 7z payload is what ships, and its 30 s health deadline can be too short on a dev machine while ~111 MB is unpacked alongside another running instance.
- Electron's single-instance lock is namespaced by the userData directory, so a packaged portable exe can be smoke-tested alongside a user's running instance by pointing `LLM_PROXY_DATA_DIR` at a fresh dir and `--port` at a free ephemeral port (combine with `LLM_PROXY_SMOKE_EXIT_FILE` for clean shutdown, as `scripts/artifact_smoke.ts` does). This shell expands `$_`, which breaks PowerShell one-liners (`$_` becomes `/usr/bin/bash.ProcessName`) — run PowerShell logic from a `.ps1` file or use `tasklist`; `Get-CimInstance Win32_Process` with `CreationDate`/`ExecutablePath`/`CommandLine` is what tells the user's instance apart from a smoke launch. Spawning Node from a script in this shell needs `process.execPath` (`spawn("node", …)` fails with `spawn node ENOENT`), and a bash `/tmp/...` cwd is not usable for a Windows child process — take the throwaway cwd from `os.tmpdir()`, and give the executable an absolute `path.resolve(...)` there, because a relative exe path is resolved against that cwd and fails with `spawn ... ENOENT`. After `npm run rebuild:electron`, a plain-Node run of the DB-backed admin APIs returns 500 `ERR_DLOPEN_FAILED`: that is the Electron-ABI state of `better-sqlite3`, not a bug in the app.
- History log roots resolve relative to the **application config file's directory** (`logRootBaseDirectory: path.dirname(options.applicationConfigFile)` in `src/app/runtime.ts`), not the child's cwd and not `--log-root` alone. A smoke run whose `--application-config` is a throwaway copy therefore shows an empty history (0 groups, and every task-brief endpoint 404) even when the real log root is named — pass the portable app's own `llm-proxy.json` (the app only writes it when missing) while keeping `LLM_PROXY_DATA_DIR` fresh for the single-instance lock. The production `traffic.db` is ~10 GB: give a real-data launch a generous health deadline and prefer pointing at the real log root over copying that file. Copy the pairs config instead and move its `listen_port` off the port the user's instance holds — and move `summary_model.target_url` with it when it points back at that same listener, or the model call hits a dead port.
