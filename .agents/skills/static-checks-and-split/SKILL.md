# Numbered classic scripts and their static checks

These traps were learned in this repository and moved here verbatim from `AGENTS.md`;
nothing was paraphrased.

- The admin UI is authored as numbered classic scripts (`src/admin/static/01-core.js` … `09-wiring.js`) that the server concatenates into the single `/static/app.js` the browser runs; the URL, `index.html` and routes are unchanged, so every probe technique that intercepts `**/static/app.js` still works. Two structural rules: top-level executed statements live only in `09-wiring.js` (it must stay last, because load order runs them once and earlier files may be referenced by later ones, never the reverse) and `const state` is declared exactly once (a second top-level declaration of the same name in any part is a load-time SyntaxError, not a runtime one). `npm run lint` first runs `tsx scripts/concat_ui_parts.ts` to write the same concatenation to gitignored `.ui-check/app.js` and lints that file — linting the parts individually gives ESLint one script scope per file, so every cross-file reference reads as `no-undef` (measured 2034 false positives for a 7k-line UI that lints clean as one file). `npm run typecheck` also checks the parts through `tsconfig.ui.json` (`allowJs`+`checkJs`, `strict: false`), which must set `moduleDetection: "legacy"`: this repo is a `"type": "module"` package, so `module: NodeNext` treats extension-less `.js` files with no imports as ES modules, each with its own scope, and every cross-file global turns into TS2304/TS2592 (measured 1943 bogus errors versus 0 with `legacy`). Mechanical typing rewrites (`asElement`, `qsOn`, `closestOn`, `String(...)` wrappers) change runtime code, so the UI suite with pixel baselines is the only proof they are behavior-neutral; `test-node/admin/static-source.test.ts` asserts the authored part order equals `ADMIN_SCRIPT_PARTS`, which catches a renumbered part that the server would still load in its explicit order.
- The DOM lookups (`$`, `qs`, `qsOn`, `asElement`, `closestFrom`, `closestOn`, `parentOf`) are declared `UiElement | null`, which is what the DOM returns. With `strictNullChecks` off that union collapses, so the honest annotation adds no diagnostic: `qs("#missing").value.trim()` still type-checks clean, and across the nine scripts 325 lookup sites use only 55 `?.` guards. To re-measure what enabling the flag would cost, write a throwaway config that extends `tsconfig.ui.json` and sets one compiler option, run `npx tsc -p <that config> --noEmit > file.log`, then count `error TS` lines in that file (never through a pipe). Measured: 614 with `strictNullChecks: true` (203 TS2531, 196 TS18047) after the honest unions, 207 before them, and 1296 with `strict: true`. Deleting the throwaway config is part of the recipe - only `tsconfig.json`, `tsconfig.ui.json` and `tsconfig.build.json` are permanent; since AI-15 the product compile runs through the third one and the first emits nothing.
- `test-node/admin/static-source.test.ts` formats every browser script part and asserts the concatenation keeps one placeholder plus no duplicate top-level declarations, so run `npx prettier --write` on the static files before the full suite - that single guard fails first and is faster than eyeballing formatting. Throwaway browser probes hit the same wall the admin tests already respect: `/api/load-balancer/status` has `additionalProperties: false` with a long `required` list, so a stub fixture missing `canonicalKey`/`failures`/`inRotation` answers 500 and the probe waits for a poll that never fills anything.
